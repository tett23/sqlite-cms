# 0043 ヘッダのカスタマイズ

## 状態

提案。

## 決定

記事リポジトリに `content/header.md` を書くと、ヘッダをその内容にする。
書かなければ、今までどおりの既定のヘッダ（サイト名、案内、検索ボックス）を出す。

### 書き方

`content/header.md` は frontmatter のない Markdown で、本文と同じ記法（ADR 0025）を使える。
site.toml の値を、Mustache のような書き方で埋め込める。

| 書き方 | 意味 |
|---|---|
| `{{name}}` | 値を文字として埋め込む。Markdown の記号をバックスラッシュでエスケープする |
| `{{{name}}}`、`{{& name}}` | 値をそのまま埋め込む（Markdown として読まれる） |
| `{{#name}}…{{/name}}` | 値があれば中身を描く。中では、その値の中の名前も使える |
| `{{^name}}…{{/name}}` | 値がなければ中身を描く |
| `{{! 注釈}}` | 何も描かない |
| `{{> search}}` | 検索ボックスを置く。一行に単独で書く |

- 名前は `license.name` のように `.` でたどれる。`{{.}}` はいまの値を表す。
- 使える値は `title`、`author`、`description`（省略したときは site.toml から組み立てたもの）、`url`（`/` で終わる形）、`license`（`name`、`url`）。
- 値のない名前と空の文字列は「値がない」とみなし、埋め込むと空になる。
- セクション、注釈、パーシャルのタグだけの行は、行ごと取り除く（Mustache の standalone の規則）。タグの行が空行として残り、Markdown のリストや段落が分かれるのを避けるためである。
- 区切りを変える書き方（`{{=<% %>=}}`）、リスト、ラムダ、パーシャルの字下げには対応しない。埋め込む値にリストや関数がないためである。

### エスケープ

Mustache の `{{name}}` は HTML のエスケープをするが、ここでは埋め込む先が Markdown なので、Markdown の記号（`\` `` ` `` `*` `_` `[` `]` `<` `>` `&` `$` `~` `|` `!` `{` `}`）をバックスラッシュでエスケープする。
サイト名に `*` や `[` を含んでも、文字のまま表示される。
バックスラッシュのエスケープは、コード、自動リンク、HTML の属性の中では効かないので、そこでは `{{{name}}}` を使う（README に書く）。
値は書き手自身の site.toml から来るので、エスケープは表示を崩さないためのもので、安全のためではない（本文と同じく、SPA が HTML を無害化する、ADR 0018）。

### 自前の実装

Mustache のようなものは、依存を足さずに自前で書く（`cli/src/mustache.rs`）。
字句（文字列とタグ）に分け、セクションを入れ子の木にし、値の文脈を積み上げながら描く。
書き誤り（閉じていないタグやセクション、対応しない閉じタグ、知らないパーシャル、単独でないパーシャル、使えない名前）は、行番号付きで返す。

### 埋め込むのはビルドのとき

値の埋め込みは、SPA ではなく CLI がビルドのときに行い、埋め込んだ Markdown を DB の `site.header_md` に入れる（マイグレーション 0007）。

- 書き誤りを、ビルドのときに `content/header.md の 3 行目: …` のように知らせられる。ブラウザで見て初めて気付くことがない。
- 埋め込む処理をブラウザに送らずに済む。
- site.toml の値は DB を作るときに決まっているので、ブラウザで埋め込む理由がない。

### 検索ボックスの置き場所

`{{> search}}` を、CLI は `<div class="partial-search"></div>` に置き換える（前後に空行を置き、HTML のブロックが前後の段落とつながらないようにする）。
SPA の本文の部品（`MarkdownBody`）は、渡された部品（`partials`）で、この目印を検索ボックスにする。
本文の無害化（ADR 0018）では、`partial-search` のクラスを持つ `div` を残す。記事の本文に同じものを書いても、部品を渡さないので何も描かない。

### 見た目

ヘッダの Markdown は、本文（`article-body`）ではなく `site-header-body` の見た目で描く。

- 最初の段落を、既定のヘッダのサイト名と同じ大きさと太さで左に置く。
- ほかの段落、リスト、検索ボックスを、右に横に並べる。狭い画面では折り返す。
- リストは黒丸を付けずに横に並べる。画像は高さ 2.5rem までにする。

### DB を読むまで

カスタムのヘッダは DB を読むまで中身が分からない。
既定のヘッダを先に描くと、DB を読んだときに差し替わり、一瞬別のヘッダが見え、表示もずれる。
そこで、CLI は `content/header.md` があるときに、`index.html` に `<meta name="sqlite-cms-header" content="custom">` を入れる。
SPA はこれがあれば、DB を読むまでヘッダも本文も描かず、`index.html` と同じ読み込み中の表示だけを出す。なければ今までどおり既定のヘッダをすぐに描く。
空のヘッダを先に描くと、DB を読んでヘッダの中身が入ったときに本文が押し下げられ、Cumulative Layout Shift が 0.05〜0.08 になった。

あわせて、各ページの部品は、DB が読み込み済みなら最初の描画から使う（`useDb`）。
これまでは読み込み済みでも一度読み込み中の表示を描いてから本文に替えていたので、ヘッダと本文を同時に描くようにすると、読み込み中の表示のすぐ下に描いたフッタが押し下げられた（Cumulative Layout Shift が 0.08）。
ページを移るたびに読み込み中の表示が一瞬見えることもなくなる。

見本（カスタムのヘッダ）の計測で、数式の描画でずれるページ（ADR 0040）を除き、すべてのページの Cumulative Layout Shift が 0 になることを確かめた。
Vite の開発サーバー（`--data-only`）では `index.html` に目印がないので、既定のヘッダが一瞬見えてから差し替わる。

### そのほか

- ヘッダに URL だけの行を書くと、本文と同じくリンクカードになる。そのため、リンクカードの画像を集めるときに、埋め込んだヘッダも読む。
- `init` は `content/header.md` を作らない。既定のヘッダで足りる人には要らないからである。見本（`example/`）には、既定のヘッダと同じ見た目になるものを置く。

## 実装しないこと

- ヘッダ以外（トップページ、記事）での値の埋め込み。
- 記事ごとの値（記事の題名など）の埋め込み。ヘッダはすべてのページで同じものを使う。
- フッタのカスタマイズ。
- 検索ボックス以外のパーシャル。

## テスト設計

- Mustache：変数のエスケープとそのままの埋め込み、`.` でたどる名前と値のない名前、セクションと反転セクション（値のない場合と空の文字列）、行ごと取り除くタグ（CRLF を含む）と取り除かないタグ、パーシャル（単独でないときと知らないときの誤り）、書き誤りの行番号、タグのない文字列。
- DB：site.toml の値を埋め込んだヘッダが入ること、なければ NULL、書き誤りでファイル名と行番号を知らせること。
- index.html：`content/header.md` があるときだけ目印を入れること。
- SPA：DB からヘッダを読むこと。目印を渡した部品に置き換え、部品がなければ何も描かないこと。
- ヘッドレスの Chrome で、見本のヘッダが既定のヘッダと同じ見た目になり、リンクがページを読み直さずに移り、検索の候補が出ることを確かめた。

## トレードオフ

- カスタムのヘッダは DB を読んだ後に現れるので、既定のヘッダより表示が遅い。
- 最初の段落をサイト名として扱うのは暗黙の約束である（README に書く）。
- エスケープが効かない場所（コード、自動リンク、HTML の属性）では、書き手が `{{{name}}}` を選ぶ必要がある。
