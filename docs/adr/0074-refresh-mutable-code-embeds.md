# ADR 0074: 中身が変わるコードの埋め込みは、組み立てるたびに取り直す

ステータス: 採択

## 文脈

コードの埋め込み（[ADR 0065](0065-embed-github-files-and-gists.md)）は、URL だけの行の GitHub のファイルと Gist の中身を、サイトを組み立てるときに取得し、記事リポジトリの `.sqlite-cms-cache/code-embeds/` に保存する。
保存した結果があれば、取得し直さない。保存した結果に期限はなく、取り直すにはキャッシュを消す必要がある。

そのため、元のファイルや Gist を更新しても、手元の `serve` や `build` には古い中身が出続ける。
これは [ADR 0065](0065-embed-github-files-and-gists.md) のトレードオフに書いたとおりの動きだが、利用者からは「ファイルを更新しても直らない」と見え、キャッシュを消すことに気付きにくい。

中身が変わるかどうかは、URL で分かる。

- GitHub のファイルで、`<ref>` がコミットの SHA（40 桁の 16 進数）のもの（パーマリンク）は、中身が変わらない。
- `<ref>` がブランチ名やタグ名のもの（`/blob/main/…`）と、Gist（`gist.github.com/<user>/<id>`。版を指定する URL は対象にしていない）は、中身が変わりうる。

## 実装すること

### 中身が変わる URL は、取り直す

- サイトを組み立てるとき（`build`、`serve`、`deploy`）、通信できるなら（`SQLITE_CMS_OFFLINE` でないなら）、中身が変わりうる URL は、保存した結果があっても取り直す。
  - 取り直せたら、その結果を使い、保存し直す。
  - 取り直せなければ、警告を出して、保存した結果を使う。保存した結果もなければ、今までどおりリンクカードにする。
- コミットの SHA の URL は、今までどおり、保存した結果があれば取り直さない。
- 中身が変わるかは、`<ref>` が 40 桁の 16 進数かだけで決める。短い SHA（7 桁など）は、ブランチ名と見分けられないので、中身が変わりうるものとして扱う。

### serve では、起動したときだけ取り直す

- `serve` は、記事を保存するたびに組み立て直す（[ADR 0034](0034-serveの自動反映.md)）。そのたびに通信すると、反映が遅れ、GitHub の API の回数の制限（Gist、1 時間に 60 回）にも当たりやすい。
- そこで、`serve` は、起動したときの組み立てでだけ取り直し、記事の変更で組み立て直すときは、保存した結果を使う。保存した結果のない URL（新しく書いた URL）は、今までどおり取得する。

### 通信しないとき

- `SQLITE_CMS_OFFLINE` のとき（CI のブラウザの検査、[ADR 0066](0066-offline-browser-checks-with-committed-cache.md)、結合テスト）は、今までどおり取得せず、保存した結果だけを使う。見本のキャッシュは取り直さない。

### 文書

- README のコードの埋め込みの説明を改める（中身が変わる URL は組み立てるたびに取り直すこと、`serve` は起動したときだけであること、コミットの SHA の URL を勧めることは残す）。
- specifications.md のコンテンツフォーマットに書き足す。
- DEVELOPMENT.md の、見本のキャッシュを取り直す手順に、中身が変わる URL は組み立てるたびに取り直されることを書く。

## 実装しないこと

- リンクカードの画像（[ADR 0028](0028-リンクカードの画像.md)）を取り直すこと。ページの画像は変わることが少なく、取得の数も多い。
- 保存した結果に期限を付けること、取り直すコマンドやオプションを足すこと。
- Gist の版を指定する URL（`gist.github.com/<user>/<id>/<版>`）を対象にすること。
- 取り直したときに、中身が変わったかを知らせること。

## テスト設計

- 中身が変わるかの判断：`/blob/<40 桁の SHA>/…` は変わらない。`/blob/main/…`、`/blob/v1.0/…`、`/blob/0123abc/…`（短い SHA）、`/blob/feature/x/…`、Gist は変わりうる。
- 偽の取得（[ADR 0065](0065-embed-github-files-and-gists.md) のテストと同じ `Fetcher` の差し替え）で、次を確かめる。
  - 保存した結果がある、中身が変わりうる URL を、取り直し、新しい中身を使って保存し直すこと。
  - 取り直せなければ、保存した結果を使うこと。
  - 保存した結果がある、コミットの SHA の URL は、取り直さないこと。
  - オフラインでは、どちらも取り直さないこと。
  - 取り直さない設定（`serve` の組み立て直し）では、保存した結果のある URL を取り直さず、保存した結果のない URL だけを取得すること。
- 結合テスト：`serve` を起動したときの組み立てと、記事を変えたときの組み立て直しで、取り直すかが変わることは、単体テストで確かめる（結合テストは通信しないため）。
- `example_has_cached_results_for_every_url`（[ADR 0066](0066-offline-browser-checks-with-committed-cache.md)）が、今までどおり通ること。

## トレードオフ

- 中身が変わる URL があると、`build` と `deploy` のたびに通信するので、組み立てが遅くなる。記事に書く数は多くないと考える。
- Gist の取り直しは GitHub の API を使うので、組み立てを何度も繰り返すと、回数の制限（1 時間に 60 回）に当たりうる。当たったら、保存した結果を使う。
- `serve` の起動中に元のファイルを更新しても、起動し直すまで反映されない。
- 見本のキャッシュ（[ADR 0066](0066-offline-browser-checks-with-committed-cache.md)）は、手元で見本を組み立てると、Gist の中身が変わっていれば書き換わり、`git status` に出る。そのときは、取り直した結果をコミットする。
