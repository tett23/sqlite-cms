# ADR 0065: GitHub のファイルと Gist の中身を本文に表示する

ステータス: 採択

## 文脈

URL だけの行は、リンクカードになる（ADR 0025、0028、0049）。
GitHub のファイル（`https://github.com/<owner>/<repo>/blob/<ref>/<path>`）や Gist（`https://gist.github.com/<user>/<id>`）の URL を貼っても、カードにはホスト名と URL と OGP の画像しか出ず、コードの中身は読めない。
記事でコードを示したいとき、今は中身を本文のコードブロックに写すしかなく、元のファイルとずれていく。

GitHub と Gist が配る埋め込み（`<script src="https://gist.github.com/….js">`）は使えない。
閲覧のときにほかのサイトと通信しない方針（ADR 0028）に反し、本文で許す HTML（ADR 0018）でも `script` は取り除く。
また、ブラウザから GitHub の中身を取りに行くと、閲覧者の情報が GitHub に渡り、遷移をネットワークなしで済ませる作り（DB を最初に読み、以後は DB だけで描く）にも反する。

そこで、リンクカードの画像と同じく、CLI がサイトを組み立てるときに中身を取得して DB に入れ、SPA がコードブロックとして描く。

## 実装すること

### 対象の URL

URL だけの行（リンクカードになる行）のうち、次の形の URL を、中身を表示する埋め込み（以下、コードの埋め込み）にする。

- GitHub のファイル：`https://github.com/<owner>/<repo>/blob/<ref>/<path>`
  - 末尾に行の範囲 `#L<n>` か `#L<n>-L<m>` があれば、その行だけを表示する。範囲がファイルの行数を超えるところは切り詰める。範囲がまったくファイルにないときは、取得の失敗と同じに扱う。
  - `<ref>` は、ブランチ名、タグ名、コミットの SHA のどれでもよい。`/` を含むブランチ名も、そのまま扱う（取得先の URL に写すだけで、`<ref>` と `<path>` を分ける必要がない）。
- Gist：`https://gist.github.com/<user>/<id>` と `https://gist.github.com/<id>`
  - 末尾に `#file-<名前>` があれば、そのファイルだけを表示する。`<名前>` は、GitHub と同じく、ファイル名を小文字にして英数字以外を `-` にしたものと比べる。合うファイルがなければ、取得の失敗と同じに扱う。
  - なければ、Gist のすべてのファイルを、Gist の並び順に表示する。

`http`、クエリ文字列のあるもの、`/raw/`・`/tree/`・`/blame/` などほかの形の URL は対象にせず、今までどおりリンクカードにする。

### 取得（CLI）

リンクカードの画像（ADR 0028）と同じときに、同じ決まりで取得する（`build`、`serve`、`deploy`。1 件あたり 10 秒で打ち切る。User-Agent は `sqlite-cms/<版> (code embed)`）。

- GitHub のファイル：`https://raw.githubusercontent.com/<owner>/<repo>/<ref>/<path>` を取得する。
- Gist：`https://api.github.com/gists/<id>` の JSON を取得し、各ファイルの名前と中身を読む。中身が切り詰められている（`truncated` が真）ファイルは、`raw_url` から取得し直す。`raw_url` が `https://gist.githubusercontent.com/` で始まらなければ使わない。

中身は次のときに使わない（取得の失敗と同じに扱う）。

- UTF-8 として読めないもの、NUL を含むもの（画像などのバイナリ）。
- 一つの埋め込みの中身の合計が 100 KB を超えるもの（行の範囲があるときは、切り出した後の大きさで比べる）。

取得できなかったものは警告を出して飛ばし、その URL は今までどおりリンクカードにする（OGP の画像も今までどおり取得する）。
取得できたものは、リンクカードの画像を取得しない。

### キャッシュ

取得した結果を、記事リポジトリの `.sqlite-cms-cache/code-embeds/<URL の BLAKE3 の先頭 16 文字>.json` に保存する（ファイル名、中身、取得元の URL）。
保存した結果があれば、取得し直さない。失敗したものは保存せず、次のビルドで取得し直す。
`SQLITE_CMS_OFFLINE` のときは取得せず、保存した結果だけを使う。
ブランチ名の URL は、元のファイルが変わってもキャッシュを消すまで古い中身のままになるので、README でコミットの SHA の URL（パーマリンク）を勧める。

### DB

マイグレーション 0012 で、表 `code_embed_files` を足す。一つの URL に、表示するファイルの数だけ行を入れる。

| 列 | 中身 |
|---|---|
| `url` | 本文に書かれた URL（行の範囲や `#file-` を含む） |
| `position` | URL の中での並び順（0 から） |
| `file_name` | ファイル名（GitHub のファイルは `<path>` の最後の部分） |
| `source_url` | 見出しのリンク先（GitHub のファイルは本文の URL、Gist は `<Gist の URL>#file-<名前>`） |
| `start_line` | 最初の行の番号（行の範囲がなければ 1） |
| `content` | 中身（行の範囲があれば、その行だけ） |

中身は本文と同じく DB に入れる。遷移をネットワークなしで済ませるためである（文脈）。
全文検索（ADR 0031）の対象にはしない。検索するのは記事に書いた文章であり、ほかのリポジトリのコードではないためである。

### 表示（SPA）

- URL だけの段落のうち、DB の `code_embed_files` に URL があるものを、リンクカードの代わりにコードの埋め込みにする。
- ファイルごとに、見出しとコードブロックを出す。
  - 見出しには、ファイル名と、GitHub のファイルなら `<owner>/<repo>` と行の範囲（`L10-L20`）、Gist なら `Gist` と書き、`source_url` へのリンクにする（外へのリンクなので新しいタブで開く。ADR 0057）。
  - コードブロックは、本文のコードブロックと同じく Shiki で色を付ける（ADR 0017）。言語は、ファイル名の拡張子から、本文のコードブロックで使える言語（`highlightLanguages.ts`）に当てはめる。当てはまらなければ色を付けない。
  - 行番号を、コードの左に出す。行の範囲があれば、その最初の行（`start_line`）から数える。元のファイルのどこかが分かるようにするためである。
    - 行番号は、CSS のカウンタ（Shiki が出す行ごとの `span.line` に `counter-increment` を付け、`::before` で番号を描く）で描き、`counter-reset` で `start_line` から始める。番号は文字として本文に入らないので、コードを選んで写したときに番号が混ざらない。
    - 番号の欄の幅は、最後の行の番号の桁数に合わせ（`ch` で指定する）、番号は右に寄せる。番号の色は本文のコードより薄くし、横に巻き取っても番号は残す（`position: sticky`）。
    - 本文のコードブロックには、今までどおり行番号を出さない。
- 高さは `max-height: 30rem` に抑え、超えたら縦に巻き取る。長いファイルで本文が読みにくくならないようにするためである。
- DB にない URL（取得に失敗したもの、対象でない URL）は、今までどおりリンクカードにする。

### 文書と見本

- README の拡張の記法に、コードの埋め込みの書き方と、パーマリンクを勧めることを書く。
- specifications.md のコンテンツフォーマットとディレクトリ構成（`.sqlite-cms-cache/code-embeds/`）に書き足す。
- 見本の「記法の一覧」に、このリポジトリのファイル（コミットの SHA のパーマリンク、行の範囲あり）と、Gist の埋め込みを一つずつ足す。

## 実装しないこと

- 非公開のリポジトリと秘密の Gist。トークンを使わずに読めるものだけを対象にする。トークンを扱うと、CI や `.env` での受け渡しと、漏れたときの影響を考える必要が出る。
- GitHub の API の回数の制限（認証なしで 1 時間に 60 回）への対処。Gist の取得だけが API を使い、結果はキャッシュするので、ふつうの記事の数では足りる。超えたら取得の失敗と同じに扱い、リンクカードにする。
- GitHub のファイル以外（GitLab、Bitbucket、raw の URL など）。
- ブラウザでの取得と、閲覧のときの最新の中身への更新。
- 行の範囲の強調、折りたたみ。
- 本文のコードブロックへの行番号の表示。
- Markdown のファイルを、Markdown として描くこと。中身はコードとして表示する。
- RSS（ADR 0033）での中身の表示。RSS には、今までどおり URL が載る。

## テスト設計

- CLI（Rust の単体テスト）
  - URL の判定：ファイルの URL（行の範囲なし、`#L10`、`#L10-L20`、`/` を含むブランチ名）、Gist の URL（ユーザー名あり・なし、`#file-` あり・なし）を対象にし、`http`、クエリ文字列、`/raw/`・`/tree/` の URL、ほかのホストを対象にしないこと。
  - 取得先の URL：ファイルの URL から raw の URL を、Gist の URL から API の URL を作ること。
  - 行の切り出し：範囲の中、範囲がファイルの終わりを超えるとき（切り詰める）、範囲がまったくないとき（失敗）。改行が CRLF のとき。
  - Gist の JSON：複数のファイルの並び順、`#file-` の名前の比べ方（大文字、`.`、`_` を含むファイル名）、`truncated` のときに `raw_url` から取り直すこと、`raw_url` のホストが違うときに使わないこと。
  - 使わない中身：UTF-8 でないもの、NUL を含むもの、100 KB を超えるもの。
  - 偽の取得（今の `Fetcher` の差し替え）で、成功したものが `code_embed_files` に入り、リンクカードの画像を取得しないこと。失敗したものが入らず、リンクカードの画像を取得すること。
  - キャッシュ：保存した結果で取得し直さないこと、失敗を保存しないこと、`SQLITE_CMS_OFFLINE` で取得しないこと。
- SPA（vitest）
  - `code_embed_files` に URL がある URL だけの段落が、見出しとコードブロックになり、ない段落はリンクカードのままであること。
  - Gist の複数のファイルが、並び順どおりに出ること。
  - 見出しのリンクが新しいタブで開くこと。拡張子から言語が決まり、決まらないときは色を付けないこと。
  - 中身の `<script>` などが、文字のまま出ること（HTML として解釈しない）。
  - 行番号が `start_line` から始まること（範囲なしは 1、`#L10-L20` は 10）。番号の欄の幅が、最後の行の番号の桁数に合うこと。本文のコードブロックに行番号の指定が付かないこと。
- E2E
  - 見本の「記法の一覧」で、コードの埋め込みが Shiki で色付けされて出ること、見出しのリンク先が合っていること、ほかのリンクカードの数が変わらないこと。
  - 行の範囲のある埋め込みで、最初と最後の行の `::before` の番号が範囲の最初と最後の番号であること。コードを選んで写した文字列（`Selection.toString()`）に番号が入らないこと。
  - CI では、今のリンクカードの画像と同じく、ビルドのときに GitHub から取得する。

## トレードオフ

- 中身を DB に入れるので、埋め込みの分だけ DB が大きくなり、最初の表示が遅れる。一つの埋め込みを 100 KB までに抑える。
- ブランチ名の URL は、キャッシュを消すまで古い中身のままになる。CI で公開するときは毎回取得し直すので、手元のプレビューと公開したサイトで中身が違うことがある。
- 取得に GitHub が要るので、GitHub が落ちているときや回数の制限を超えたときは、リンクカードに戻る。ビルドは止めない。
- Gist の取得だけ API を使うので、ファイルとは違う制限を受ける。
- 他人のコードをサイトから配ることになる。ライセンスの扱いは、URL を書いた人の責任とし、CLI は確かめない。
