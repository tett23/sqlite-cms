# 0006 ビルダーの Rust 化

## 状態

採用。0001 と 0005 の「ビルドスクリプトは TypeScript（tsx + sql.js）」という実装を置き換える。
スキーマ、マイグレーションの規約、成果物の形式は変えない。

## 決定

Markdown から SQLite を生成する処理を、Rust の単一バイナリ `build-db` として `build-db/` に置く。
TypeScript 版（`scripts/`）は削除する。

### 構成

- `content.rs`：frontmatter の分離と検証、Markdown の HTML 変換。
- `migrations.rs`：マイグレーションの読み込みと適用（ADR 0005 の規約どおり）。
- `build.rs`：DB の構築、ファイル名の決定、`public/db/` への書き出し。
- `main.rs`：第一引数をリポジトリルートとして受け取る（省略時はカレントディレクトリ）。

### 依存

- rusqlite（`bundled`）：SQLite 本体をバイナリに同梱する。ビルド環境の SQLite に依存しないため、同じ crate バージョンなら同じ入力から同じバイト列が得られる。
- pulldown-cmark：Markdown の変換。表、取り消し線、脚注を有効にする。
- serde_yaml：frontmatter の解釈。

DB はメモリ上で構築し、`sqlite3_serialize` でバイト列を取り出す。
一時ファイルを経由しないため、ジャーナルなどの副産物が成果物に混ざらない。

### npm との接続

- `npm run build:db` は `cargo run --release` でバイナリを実行する。
- `npm test` は `cargo test` のあとに vitest を実行する。
- フロントエンドのクエリのテストは、`migrations/*.sql` を sql.js で直接適用してスキーマを得る。

## 実装しないこと

- ビルド済みバイナリの配布。CI は毎回ソースからビルドし、cargo のキャッシュで時間を抑える。
- TypeScript 版との並存。二つの実装は frontmatter の検証規則がずれる原因になる。
- 増分ビルド。全件を作り直しても、記事数百件の規模では一瞬で終わる。

## テスト設計

`cargo test` で次を検証する。

- 種別ごとの frontmatter 検証（必須キーの欠落、日付の形式、article の任意キー）。
- マイグレーションの昇順読み込み、不正なファイル名の拒否、全件適用と記録、適用済みのスキップ。
- 三種別のフィクスチャから生成した DB の各テーブルの内容。
- 不正な文書でビルドが失敗すること。
- 同一入力から同一のファイル名が得られること。
- 書き出し時に旧 DB が消え、マニフェストが新しいファイル名を指すこと。

Rust で生成した DB を sql.js が読めることは、ブラウザでの表示で確認する。

## トレードオフ

- ローカルと CI の両方に Rust のツールチェーンが要る。Node だけで完結していた構成より、初回のセットアップが一段増える。
- HTML の出力が marked から pulldown-cmark のものに変わる。どちらも CommonMark に従うため本文の構造は同じだが、空白や属性の細部は一致しない。DB は毎回作り直すので、移行の作業は生じない。
- YAML の日付は、serde_yaml では文字列のまま得られる。gray-matter のように Date 型へ変換されないため、タイムゾーンによる日付のずれが起きる余地がなくなる。
