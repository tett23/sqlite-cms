# 0049 リンクカードの WebP と後からの読み込み

## 状態

提案。
0028 の「取得したリンクカードの画像を、そのまま配信する」を、カードの大きさの WebP にして配信する形に改める。
0028 の「URL だけの行を、remark の変換でカードにする」を、後から読み込む部品が描く形に改める。

## 決定

### 画像を WebP にする

リンクカードの画像は、CLI がビルドのときに取得した OGP の画像（0028）を、そのまま配信していた。
OGP の画像は 1200 × 630 px ほどの大きさがあり、見本のカードでも 1 枚 113 KB あった。
カードでは 7.5rem × 3.9rem（120 × 62 px）で表示するので、ほとんどが無駄である。

そこで、ビルドのときに、カードの大きさに縮めた WebP にする（`cli/src/cardimage.rs`）。

- 大きさは、高精細の画面に合わせて表示の 2 倍の 240 × 126 px にする。縦横比が違えば中央を切り抜く（表示の `object-fit: cover` と同じ）。
- 非可逆の WebP（品質 80）にする。見本の 2 枚は 113 KB が 2.5 KB に、41 KB が 2.0 KB になった。
- 配信するパスは `/link-cards/<URL のハッシュ>.webp` にする。
- 取得した元の画像は、今までどおり `.sqlite-cms-cache/link-cards/` に保存する。作った WebP も、元の画像の中身のハッシュの名前（`<ハッシュ>.240x126.webp`）で保存し、次のビルドからはそれを使う。元の画像を取り直せば、名前が変わるので作り直す。`serve` の自動反映（0034）で組み立て直すたびに変換しないためである。
- WebP にできない画像（AVIF、SVG、壊れた画像）は、警告を出して、取得したまま配信する。
- 縦か横が 8192 px を超える画像は読まない。ファイルは小さくても、展開すると大きな画像で、メモリを使い果たさないようにするためである。

#### 依存

画像を読んで縮める処理と、WebP の書き出しを自前で書くのは大きすぎるので、依存を足す。

- `image`（PNG、JPEG、GIF、WebP の読み込みと縮小）。純粋な Rust で書かれている。使う形式の機能だけを有効にする。
- `webp`（libwebp を使う非可逆の WebP の書き出し）。`image` の WebP の書き出しは可逆だけで、可逆では見本の画像が 10 KB 前後になり、写真ではさらに大きくなる。libwebp は C で書かれていて、ビルドのときに一緒にビルドするので、C コンパイラが要る（DEVELOPMENT.md に書く）。

リリースのバイナリは、手元の macOS で約 12.9 MB から約 13.4 MB になった（以前のビルドとの比較なので目安）。

### カードの部品を後から読み込む

カードを描く部品を、本体とは別のチャンク（`web/src/render/LinkCard.tsx`）にし、URL だけの行が画面の近くに来てから読み込む。

- remark の変換は、URL だけの段落を、カードを置く場所（`div.link-card-slot`）にするだけにする。中身のリンクはそのまま残す。
- カードを置く場所の部品が、画面の近くに来たら（0038 の `useNearViewport`）カードの部品を読み込み、カードを描く。
- 読み込むまでは、中身のリンクを、カードと同じ枠の中に出す。カードと同じ最低の高さ（画像の高さと上下の余白と枠）を CSS で取り、カードに替わるときに本文がずれないようにする。
- カードの URL と画像の対応表（DB の `link_cards`）は、remark の変換に渡していたのをやめ、部品に渡す。

#### 結果

本体の JS は減らなかった。

| | 本体の JS（gzip 後） | カードの部品（gzip 後） |
|---|---:|---:|
| 前 | 73.20 KB | （本体に含む） |
| 後 | 73.27 KB | 0.26 KB |

カードの部品はもともと小さく（圧縮前で 348 バイト）、代わりに本体に、カードを置く場所の部品と読み込みの処理が加わったためである。
カードのあるページでは、要求が一つ増える。
レイアウトのずれは、Lighthouse（狭い画面）と E2E（広い画面）のどちらでも 0 だった（最初の画面にカードのあるトップページを含む）。

カードの部品が大きくなったとき（ページの題名や説明の表示、埋め込みなど）に、本体を大きくしないための形として残す。

## 実装しないこと

- AVIF の書き出し。WebP より小さくなるが、書き出しの依存がさらに大きい（C の libavif と、AV1 の符号器）。
- 画像の大きさを、画面の幅に合わせて複数作ること（`srcset`）。カードの画像は一つの大きさで表示する。
- 本文の画像（`/media/`）の WebP への変換。書き手が用意した画像は、書き手の意図した形式と大きさのまま配信する。

## テスト設計

- 変換：PNG、JPEG、GIF、WebP を、カードの大きさの WebP にすること（色が保たれること）。縦横比の違う画像は中央を切り抜き、小さな画像は引き伸ばすこと。透明を保つこと。読めない画像と、縦横の上限を超える画像はエラーにすること。
- 収集：読める画像は `.webp` のパスで、元の画像の半分より小さい WebP として配信すること。元の画像はそのまま保存すること。作った WebP を保存して使い回し、元の画像が変われば作り直すこと。読めない画像は、取得したまま配信すること（既存のテスト）。
- SPA：部品を読み込む前は、カードを置く場所の中に普通のリンクを出し、サーバーでの描画では読み込みを始めないこと。読み込んだ後は、カードと画像を描くこと。文中の URL、リンク文字列のあるリンク、http と https 以外は、カードを置く場所にしないこと。
- E2E：カードを画面の近くに来てから描き、カードの部品を読み込むこと。画像が 240 × 126 px の WebP であること。カードのないページでは部品を読み込まないこと。レイアウトがずれないこと（既存のシナリオ）。

## トレードオフ

- ビルドに C コンパイラが要るようになる。
- 縮めて非可逆にするので、画像の細部は失われる（カードの大きさでは目立たない）。
- カードの部品を後から読み込むので、カードが描かれるまで普通のリンクが見える。本体の JS は今は減らない。
