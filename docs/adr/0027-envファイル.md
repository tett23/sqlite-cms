# 0027 .env ファイル

## 状態

採用。
0011 の「認証情報は環境変数 `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` で渡す」に、`.env` から読む方法を加える。

## 決定

`deploy` が使う環境変数を、記事リポジトリの `.env` にも書けるようにする。
手元で公開するたびに `export` しなくて済むようにするためである。

### 読み方

- `SITE_DIR/.env` を読む。ファイルがなければ、これまでどおり環境変数だけを使う。
- 実際の環境変数があれば、`.env` より優先する。CI のシークレットや、一度だけ別の値で動かすときの指定を `.env` が上書きしないようにするためである。
- 空の値は、設定されていないものとみなす。`.env.example` をコピーしただけの `.env` でも、環境変数が空でも、「設定してください」のエラーになる。
- プロセスの環境変数は書き換えない。CLI が読む変数（`CLOUDFLARE_API_TOKEN`、`CLOUDFLARE_ACCOUNT_ID`、`CLOUDFLARE_API_BASE_URL`）を引くときにだけ `.env` の値を使う。`TZ` などの、CLI が自分で読まない変数は `.env` に書いても効かない（タイムゾーンは `site.toml` の `timezone` で指定する）。
- `.env` と `.env.example` は `content/` の外にあるので、`build` と `serve` と `deploy` は配信しない。

### 書き方

依存を足さず、自前で読む（`cli/src/dotenv.rs`）。

- 1 行に `名前=値` を一つ書く。名前は英字か `_` で始まり、英数字と `_` だけからなる。`=` の前後の空白は無視する。
- 先頭の `export ` は無視する。シェルで `source` できる形のファイルもそのまま読める。
- 空行と、`#` で始まる行は読み飛ばす。
- 値は、そのまま書くか、`"..."` か `'...'` で囲む。`"..."` では `\n`、`\"`、`\\` のエスケープが使え、`'...'` は中身をそのまま使う。
- 囲まない値では、空白の後の `#` から行末までを注釈とみなす。`a#b` の `#` は値の一部である。
- 同じ名前が何度も出てきたら、後のものを使う。
- 複数行にわたる値、変数の展開（`${OTHER}`）は使えない。
- 読めない行があれば、`.env の 2 行目: …` のように行番号を示してエラーにする。

### init

`init` は次を行う。

- `.env.example` を作る。`CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` を空の値で並べ、トークンに要る権限と、`.env` にコピーして使うことを注釈に書く。`--force` では作り直す。
- `.gitignore` に `.env` を書く。トークンを誤ってコミットしないためである。`.gitignore` がなければ作り、あって `.env`（か `/.env`）の行がなければ末尾に足す。すでにあれば何もしない。既存の行は消さない。
- `.env` には触れない。`--force` でも消したり上書きしたりしない。

### API トークンの権限

`deploy` が呼ぶ API は、アカウントの「Workers スクリプト：編集」（Workers Scripts Write）の権限ですべて呼べる（Cloudflare の API リファレンスで確認した）。

| API | 受け付ける権限 |
|---|---|
| アセットのアップロードの開始 | Workers Scripts Write |
| アセットのアップロード | 開始の応答の JWT で認証する（トークンは使わない） |
| Worker の更新 | Workers Scripts Write |
| workers.dev の有効化 | Workers Scripts Write |
| workers.dev のサブドメインの取得 | Workers Scripts Write、Workers Scripts Read |

README と `.env.example` には、この権限だけを付けたカスタムトークンの作り方を書く。

## 実装しないこと

- `SITE_DIR` 以外（カレントディレクトリ、ホームディレクトリなど）の `.env` を探すこと。どの記事リポジトリの認証情報かを取り違えないようにする。
- `.env` の場所を指定するオプション。
- `new`、`build`、`serve` での `.env` の読み込み。これらは環境変数を使わない。

## テスト設計

- 読み方：そのままの値、`export`、`=` の前後の空白、行末の注釈、`"..."` のエスケープと中の `#`、`'...'`、空の値、値の中の `#`、CRLF、後の値の優先、不正な行（`=` のない行、数字で始まる名前、`-` を含む名前、名前のない行、閉じない引用符、引用符の後の文字、使えないエスケープ）の行番号。
- 環境変数との優先順位：環境変数が優先されること、空の環境変数と空の `.env` の値は設定されていないとみなすこと。
- ファイルがなければ空として扱い、読めない行があればファイル名と行番号を示すこと。
- `.env.example` を読むと、二つの変数が空の値になること。
- init：`.env.example` と `.gitignore` を作ること。既存の `.gitignore` に `.env` を足し、二度目は足さないこと。`.env` を `--force` でも変えないこと。ビルドの出力に `.env.example` が入らないこと。
- 結合テスト：`.env` の認証情報で偽の Cloudflare の API に公開でき、トークンを出力しないこと。環境変数があれば `.env` より優先すること。壊れた `.env` の行番号を示してエラーになること。

## トレードオフ

- 認証情報がファイルとして手元に残る。`.gitignore` で Git には入らないが、ファイルの管理は利用者に任せる。
- 一般的な dotenv の書き方のうち、よく使うものだけを受け付ける。複数行の値や変数の展開は書けない。
