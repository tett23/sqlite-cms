# 0015 記事の雛形を作るコマンド

## 状態

採用。
0001 の「date は `YYYY-MM-DD` の形であればよい」を、実在する日付に限るよう改める。

## 決定

CLI に `new` を足し、記事の雛形のファイルを作る。

```
sqlite-cms new <post|article|page> <SLUG> [SITE_DIR] [--title <TITLE>] [--date <YYYY-MM-DD>]
```

### 作るもの

`<SITE_DIR>/content/<posts|articles|pages>/<SLUG>.md` に、種別ごとの frontmatter と空の本文を書く。

```markdown
---
title: "タイトル"
date: 2026-09-26
description:        ← article のみ
---

```

- `title` は常にダブルクォートで囲み、`"`、`\`、改行などをエスケープする。記号で始まるタイトルや `null` のような語でも、ADR 0014 の frontmatter のパーサで元の文字列に戻る。
- `--title` を省くと、タイトルは SLUG になる。
- `description` は空（値なし）で置き、書き手が埋める。
- `page` は日付を持たないので、`--date` を指定するとエラーにする。
- 本文は空にする。見本の文章を入れると、消し忘れたまま公開される恐れがある。

### 安全策

- 同じ名前のファイルがあれば上書きせずにエラーにする。書きかけの記事を消さないためである。作成は `create_new` で行い、確認と作成の間に別のプロセスが作った場合も上書きしない。
- `SITE_DIR` に `site.toml` がなければエラーにし、何も作らない。記事リポジトリの外に `content/` を作らないためである。
- SLUG は文字（Unicode の英数字を含む）、数字、`-`、`_` だけを受け付ける。ファイル名と URL の一部になるので、`/`、`..`、`.` 始まり、空白、`?`、`#`、`%` などを入れさせない。

### 既定の日付

既定の日付は、`site.toml` の `timezone` で指定したタイムゾーンでの今日とする。
省略したときは、実行した環境のタイムゾーン（環境変数 `TZ` や OS の設定）を使う。
UTC の日付では、日本時間の 0 時から 9 時に書いた記事が前日の日付になるためである。
設定で指定できるようにするのは、CI のように手元と違うタイムゾーンで動く環境でも、同じ日付の決め方にできるようにするためである。

`timezone` には二つの書き方を受け付ける。

- **IANA の名前**（`Asia/Tokyo`、`America/New_York` など）：夏時間を含めて正しく扱える。OS のタイムゾーンデータベースで解決する。
- **UTC からの時差**（`+09:00`、`-05:30`、`UTC`）：データベースを使わないので、どの環境でも同じ結果になる。範囲は ±14:00 まで。

書式は `site.toml` を読むときに検査する。
名前がデータベースにあるかは、`new` が実際に日付を求めるときにだけ確かめる。
`build` と `deploy` は時刻を使わないので、データベースのない環境でも動く。

Rust の標準ライブラリはタイムゾーンを扱わないので、Unix では C ライブラリの `tzset` と `localtime_r` を直接呼ぶ。

- `struct tm` は、POSIX で順序が決まっている先頭の 9 つの `int` だけを読み、実装ごとの差（`tm_gmtoff`、`tm_zone` など）は末尾に余白を取って吸収する。
- 名前で指定されたときは、環境変数 `TZDIR` と一般的な置き場所（`/usr/share/zoneinfo` など）から、`TZif` で始まるデータベースのファイルを探す。見つかったファイルの絶対パスを一時的に `TZ` に設定して `localtime_r` を呼び、終わったら `TZ` を元に戻す。C ライブラリは知らない名前を黙って UTC として扱うので、先にファイルがあることを確かめないと、誤った日付になる。
- `TZ` の書き換えはプロセス全体に効くが、`new` の処理中は他のスレッドがないので問題にならない。

Unix 以外では、名前での指定はエラーにし、時差での指定と UTC だけを扱う。
日付の計算のためだけにクレートを足さない（ADR 0014 の方針）。

### 日付の検証

`--date` と、ビルダーが記事の `date`、`updated` を検証するときの判定を、暦どおりに実在する日付かどうか（うるう年を含む）に揃える。
これまでは形（`YYYY-MM-DD`）しか見ておらず、`2026-02-30` のような日付も通していた。

## 実装しないこと

- 記事リポジトリそのものの雛形（`site.toml` と `content/` を作るコマンド）。必要になったら別に足す。
- 作成したファイルをエディタで開くこと。
- タイトルから SLUG を作ること。日本語のタイトルから URL 向きの名前を機械的に作る方法は決めにくく、書き手が決めるほうが確実である。

## テスト設計

- 引数の解釈：既定値、すべてのオプション、種別と SLUG の欠落、不明な種別、余分な引数、実在しない日付、`page` への `--date`、ほかのコマンドでの `--title`。
- 雛形：記号、クォート、バックスラッシュ、改行、`null` を含むタイトルが、ビルダーの解釈で元に戻ること。本文が空であること。
- 作成：種別ごとのディレクトリにできること、上書きしないこと、種別が違えば同じ SLUG を使えること、`site.toml` がないと何も作らないこと、不正な SLUG と空のタイトル。
- 日付：日数から暦への変換（1970 年、うるう日、年またぎ）、時差の適用、実在する日付の判定、今日の日付が妥当な形であること。
- タイムゾーン：時差と `UTC` の書式、名前の書式（`..` や絶対パスを拒否する）、データベースのファイルの探し方（`TZif` でないファイルを無視する）、`site.toml` での指定と不正な指定。
- 結合テスト：作った雛形でそのままビルドできること、上書きしないこと、記事リポジトリの外でエラーになること。既定の日付について、UTC+14 と UTC-12 で必ず日付が異なることを使って次を確かめる。
  - 省略時は環境変数 `TZ` に従うこと。
  - `site.toml` の `timezone` が `TZ` より優先されること。
  - 時差での指定（`+14:00`、`-12:00`）が、同じ時差のタイムゾーン名と同じ日付になること。
  - データベースにない名前では `new` だけが失敗し、`--date` を指定した `new` と `build` は動くこと。

## トレードオフ

- C ライブラリを直接呼ぶ部分は `unsafe` になる。範囲を関数二つにとどめ、読み取るのは POSIX で決まった項目だけにしている。
- 名前でのタイムゾーンの指定は、OS のタイムゾーンデータベースに依存する。データベースのない最小構成のコンテナなどでは、時差での指定を使う必要がある。
- 日付の検証を厳しくしたので、これまで通っていた実在しない日付の記事は、ビルドでエラーになる。
