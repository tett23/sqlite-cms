# 0021 リリース時の Lighthouse の計測

## 状態

採用。
0019 の計測を、リリースのワークフローにも広げる。

## 決定

リリースのワークフロー（`release.yml`）でも Lighthouse を計測し、レポートを `lighthouse-reports` の Artifact に保存する。

- 計測は Linux のビルドのジョブで行い、そのジョブで作った release のバイナリ（実際に配布するもの）で `example/` を配信する。
- 計測のスクリプトは、環境変数 `SQLITE_CMS_BIN` でビルド済みのバイナリを受け取る。指定がなければ、これまでどおり `cargo run` で起動する。リリースの実行で debug ビルドを重ねて行わないためである。
- レポートは、計測が成功しても失敗しても保存する。
- アクセシビリティが 100 点を割ると、ビルドのジョブが失敗し、Release を作るジョブは動かない。基準を満たさないものを公開しないためである。

v0.0.1 では、レポートは `main` への push で動く `ci.yml` の Artifact にしかなく、タグの push で動くリリースの実行結果には含まれていなかった（タグの push では `ci.yml` が動かない）。

## 実装しないこと

- レポートを GitHub Release の添付ファイルにすること。Artifact で足りる。
- macOS のビルドでの計測。計測するのは SPA であり、どちらのバイナリにも同じものが埋め込まれている。

## テスト設計

- 手元で、release のバイナリを `SQLITE_CMS_BIN` で渡して計測が通ることを確認した。
- リリースのワークフローを手動実行し、`lighthouse-reports` の Artifact ができ、Release のジョブが飛ばされることを確認する。
- v0.0.2 のタグで、Artifact にレポートが含まれることを確認する。

## トレードオフ

- リリースの実行時間が 1〜2 分延びる。
