# 0038 表示の速さの改善

## 状態

提案。
0026 の「DEFLATE のブロックは、固定ハフマン符号のもの一つだけにする」と「起動の時にすべてを圧縮しない」を改める。
0029 の「部品が表示されたときに読み込みを始める」を、「画面の近くに来て、本文を描いた後に読み込みを始める」に改める。
0017 の「Shiki を rehype のプラグイン（`@shikijs/rehype`）として通す」を改める。
0039 で、実装しないことにした「React を小さなライブラリ（Preact など）に置き換えること」を実装した。
0040 で、埋め込んだ本体の CSS のファイルを、出力しないのではなく中身を空にして残すことにした（非同期のチャンクが依存として読み込み、404 になっていた）。

## 決定

Lighthouse のパフォーマンス（ADR 0019）を上げるため、次のことをする。
どれも、見本のサイトを `serve` で配信して計測し、効果を確かめたものである。

### 1. 大きなライブラリの読み込みを、本文を描いた後に回す

Shiki、KaTeX、mermaid の読み込み（ADR 0029）を、次の二つの条件がそろってから始める（`web/src/lazyLoader.ts` の `whenIdle`、`web/src/nearViewport.ts`）。

- それを使う部品（コードブロック、数式、図）が、画面から 200 px 以内に来たこと（`IntersectionObserver`）。長い記事の下の方にあるコードブロックのために、最初に Shiki を読まない。
- 本文が画面に描かれ（`requestAnimationFrame` の後）、ブラウザの手が空いたこと（`requestIdleCallback`、最長 2 秒）。

本文の描画（LCP）より前に大きなチャンクの取得を始めると、遅い回線では本文に要る JS と wasm と回線を取り合う。
Lighthouse の見積もり（Lantern）も、本文の描画より前に始まった取得を、本文の表示に要るものとして数える。

### 2. コードブロックを一つずつ色分けする

Shiki を rehype のプラグインとして本文全体に通すのをやめ、コードブロックの部品（`pre`）が自分のコードだけを色分けする（`highlightBlock`）。
`@shikijs/rehype` は依存から外す。

- Shiki を読み込み終わっても、本文の Markdown 全体を解析し直さない。
- 色分けはブロックごとに別のタスクで、一つずつ行う（`inTurn`）。画面にあるブロックをまとめて一度に色分けすると長いタスクになり、入力への応答（Total Blocking Time）が遅れる。
- 読み込み済みで、初めから画面の近くにあるとき（サーバーでの描画とテスト）は、最初の描画で色分けする。
- 同じ部品が別の記事のコードブロックに使い回されることがあるので、色分けの結果は、言語とコードの組と一緒に持つ。
- Shiki を読み込んだときに、言語とテーマの登録まで済ませる。最初のブロックの色分けと同じタスクで登録すると、さらに長いタスクになる。

### 3. DB と wasm を先読みする

CLI は `index.html` に、DB と sql.js の wasm の先読み（`<link rel="preload" as="fetch" crossorigin="anonymous">`）と、DB のパス（`<meta name="sqlite-cms-db">`）を入れる。

- SPA は、その meta があれば `manifest.json` を取りに行かずに DB を読む。なければ（Vite の開発サーバーなど）今までどおり `manifest.json` から DB のパスを得る。meta のパスで読めなかったときも `manifest.json` に戻る。
- sql.js の初期化（wasm の取得とコンパイル）と、DB の取得を並行して行う。
- 以前は JS を読んで実行してから `manifest.json`、DB、wasm を順に取っていたので、往復が 2 回多かった。

### 4. 本体の CSS を index.html に埋め込む

ビルドのとき、`index.html` が読むスタイルシートを `<style>` として `index.html` に埋め込む（`web/vite.config.ts` の `inlineEntryCss`）。

- 外部のスタイルシートは読み終わるまで描画を止め、そのあいだに JS が動き出すと、読み込み中の画面より先に JS の実行を待つことになる。
- 本体の CSS は約 13 KB（gzip 後で約 3.5 KB）と小さいので、`index.html` が少し大きくなるだけである。
- `url()` を含む CSS は、`index.html` からの相対のパスになってしまうので埋め込まない。KaTeX の CSS は本体の CSS ではないので、今までどおり別のファイルにする。

### 5. フッターを DB を読んだ後に描く

RSS の案内（ADR 0033）は `index.html` にあるので、フッターは DB を読む前から「RSS」だけで描かれていた。
本文が入るとフッターが押し下げられ、Cumulative Layout Shift が 0.03〜0.08 になっていた。
サイトの情報を読んだ後に、一度だけ描く。

### 6. リンクカードの画像を画面の近くに来てから読む

リンクカードの画像（ADR 0028）は、画面から 200 px 以内に来たときに初めて `src` を入れる。
`loading="lazy"` だけでは、Chrome は画面から 1,250 px 以内の画像をすぐに読み込むので、画面の外のカードの画像が本文の表示と回線を取り合っていた。
画像の大きさは CSS で固定してあるので、後から読み込んでも本文はずれない。

### 7. serve の gzip を動的ハフマン符号にし、起動時に圧縮しておく

- DEFLATE のブロックを、動的ハフマン符号のものにする（`cli/src/gzip.rs`）。LZ77 の結果の記号 65,536 個ごとにブロックを分け、ブロックごとに符号を作る。符号の長さは 15 ビット（符号の長さの符号は 7 ビット）までに抑え、超えたら出現回数をならして作り直す。
- 起動したら、別のスレッドで、配信するファイルのうち圧縮する種類のものを圧縮しておく。`index.html` が読むファイルを先にする。最初の要求で wasm の圧縮（最適化なしのビルドで約 0.3 秒）を待たないようにするためである。起動の表示は遅れない。

圧縮率は zlib（レベル 6）とほぼ同じ（1% 以内）になった。

| ファイル | 圧縮前 | 固定ハフマン符号（0026） | 動的ハフマン符号 | zlib（レベル 6） |
|---|---:|---:|---:|---:|
| 本体の JS | 621 KB | 218 KB | 193 KB | 191 KB |
| Shiki の JS | 1,068 KB | 182 KB | 161 KB | 160 KB |
| sql.js の wasm | 658 KB | 375 KB | 324 KB | 323 KB |

### 計測結果

Lighthouse のパフォーマンスは次のとおり変わった（手元の Apple Silicon、`serve` で配信、1 回ずつの計測）。
ほかの三つの分類（ユーザー補助、おすすめの方法、SEO）は、変更の前後とも全ページで 100 点である。

| ページ | 変更前 | 変更後 |
|---|---:|---:|
| `/` | 84 | 86 |
| `/articles/syntax` | 68 | 87 |
| `/articles/extensions` | 58 | 83 |
| `/articles/getting-started` | 67 | 80 |
| `/posts/ruby` | 71 | 83 |
| `/about` | 82 | 88 |
| `/search?q=記事` | 83 | 88 |
| `/archive` | 82 | 88 |

変更前のトップページの 84 点は、最初の要求で `serve` が圧縮に時間をかけたために、読み込み中の画面が JS より先に描かれた偶然による。
起動時に圧縮しておくようにしたので、トップページもほかのページと同じ条件で計測される。
トップページだけ LCP が長い（4.1 秒、ほかは 3.8 秒）のは、画面の中にあるリンクカードの画像を、本文と同時に読み込むからである。

計測ごとの揺れは数点ある（`/articles/getting-started` は 80〜82 点）。
残る減点のほとんどは LCP（3.8 秒）で、本文を描くのに要る JS（gzip 後で約 190 KB）と wasm（約 320 KB）の転送量で決まっている。
コードブロックのあるページでは、最初のブロックの色分け（Shiki が文法の正規表現を変換する）が 150 ms ほどの長いタスクになり、Total Blocking Time が 250〜340 ms 残る。

## 試して、採らなかったこと

- **Shiki の事前変換済みの文法**（`@shikijs/langs-precompiled` と `createJavaScriptRawEngine`）。最初の色分けは 1/10 以下（シェルで 42 ms から 2 ms）になるが、登録のときにすべての言語の正規表現を作るので、約 260 ms の長いタスクができ、Total Blocking Time はかえって悪くなった。使う言語だけを、言語ごとのチャンクから登録する形にすれば効く見込みがあるが、依存が増えるので見送る。
- **GFM の解析だけを登録する自前のプラグイン**（remark-gfm が登録する、Markdown を書き出す拡張を除く）。本体の JS が gzip 後で約 4.6 KB（2.4%）減るだけで、点数は変わらない見込みなので、依存を入れ替えない。
- **リンクカードの画像を、本文を描いた後に読むこと**。画像の取得は描画の直後に回せたが、Lighthouse が記録する描画の時刻はそれより遅く、見積もりは変わらなかった。

## 実装しないこと

- sql.js の wasm を小さくすること（使わない機能を外してビルドし直す）。LCP は JS と wasm の転送量でほぼ決まっているが、sql.js を自前でビルドする必要がある。
- React を小さなライブラリ（Preact など）に置き換えること。
- rehype-raw（parse5）を、本文に HTML があるときだけ読み込むこと。0018 で採らなかった。
- Brotli での圧縮。本番の Cloudflare は Brotli で配信するが、`serve` に Brotli の圧縮を自前で書くのは大きい。

## テスト設計

- 色分け：ブロックごとに色分けした結果が、今までの rehype のプラグインと同じ見た目になること（既存のテスト。クラス、背景色、diff の行）。
- 読み込み器：Shiki を読み込む前は色なしで描き、読み込んだ後は色を付けること（既存のテスト）。
- 先読み：`index.html` に DB と wasm の先読みと DB のパスが入り、サイトを置くパスから始まること。
- gzip：固定ハフマン符号のときと同じく、繰り返しの多い文章、ばらばらのバイト列、空、1 バイト、長い一致をまたぐものを、システムの `gzip -dc` で展開して元に戻ること。
- 起動時の圧縮：圧縮する種類で 256 バイト以上のファイルだけを圧縮しておくこと。

## トレードオフ

- コードブロックに色が付くのが、本文を描いた後に手が空くまで遅れる（最長 2 秒）。画面の外のコードブロックは、近くに来てから色が付く。
- 数式と図も、本文を描いた後に手が空くまで生のテキストのままになる。
- `index.html` が CSS の分（gzip 後で約 3.5 KB）大きくなり、ページを移っても CSS はキャッシュされない（SPA なのでページの移動では `index.html` を取り直さない）。
- `serve` は起動の後しばらく、圧縮のために CPU を使う。
