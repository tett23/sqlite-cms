# 0040 重いページと複雑なページの見本

## 状態

提案。
0038 の「本体の CSS を index.html に埋め込み、ファイルは出力しない」を、「中身を空にしたファイルを残す」に改める。
0025 の図（mermaid）の既定のレイアウトを dagre にする。

## 決定

### 見本の記事

表示の重さを確かめるため、見本（`example/`）に次の 6 本の article を足し、Lighthouse の計測（ADR 0019）の対象に加える（`web/scripts/lighthouse.mjs` の `PAGES`）。
どれも、冒頭のメッセージで重さを確かめるための見本であることを書く。

| 記事 | 重さの種類 | 中身 |
|---|---|---|
| `heavy-code` | コードブロックの数 | 色を付けるすべての言語で同じ処理を書いた、約 35 個のコードブロック |
| `heavy-math` | 数式の数 | 分野ごとの公式。KaTeX の要素で約 100 個 |
| `heavy-diagrams` | 図の数と種類 | 11 種類の mermaid の図（elk のレイアウトを一つ含む） |
| `heavy-long` | 本文の長さ | 約 25 KB の本文と、約 250 行の文字コードの表 |
| `complex-nesting` | 入れ子の深さ | 6 段のリスト、3 段の引用、入れ子の折りたたみとメッセージ、表の中の数式と HTML、多くの脚注 |
| `complex-mixed` | 種類の混在 | コード、数式、図、リンクカード、画像を節ごとに交互に置き、最初の画面で三つのライブラリをすべて使う |

どちらも、それぞれの記法が描けることを確かめる見本も兼ねる。
書き誤りのある数式と図を一つずつ入れ、元の文字列のまま表示されることを見せる。

見本の記事はすべて一つの DB に入るので、DB が大きくなり（gzip 後で 11 KB から約 31 KB）、ほかのページの Largest Contentful Paint も少し延びる（3.5 秒から 3.6 秒）。
本番のサイトでも記事が増えれば同じことが起きるので、見本もその状態で計測する。

### 本体の CSS のファイルを空にして残す

0038 で本体の CSS を `index.html` に埋め込み、ファイルは出力しないことにした。
ところが、mermaid の elk のチャンクなど一部の非同期のチャンクは本体のチャンクを依存に持つため、読み込むときに本体の CSS も読み込もうとして 404 になり、コンソールにエラーが出ていた（おすすめの方法が 96 点になった）。

Vite の `build.modulePreload.resolveDependencies` は CSS の依存を対象にしないので、依存から外せない。
そこで、ファイルは中身を空にして残す（コメントだけを書く）。
中身を残すと、同じ規則が後からもう一度当たり、KaTeX の CSS などとの順番が変わるおそれがある。

### 図の既定のレイアウトを dagre にする

mermaid 12 は、既定のレイアウトが elk になっている。
そのため、フローチャート、状態遷移図、ER 図などを描くたびに、指定がなくても elk（gzip 後で約 440 KB）を読み込み、elk で並べていた。
`web/vite.config.ts` の注釈に書いた「図で elk を指定したときだけ読み込む」が成り立っていなかった。

`mermaid.initialize` で `layout: "dagre"` を指定し、elk は図で `layout: elk` を指定したときだけ使う。
ヘッドレスの Chrome で、フローチャート、状態遷移図、ER 図を一つずつ置いたページでは elk を読み込まず、`layout: elk` を指定した図のあるページでは読み込むことを確かめた。

### 計測結果

Lighthouse のパフォーマンスは次のとおり（手元の Apple Silicon、`serve` で配信）。
ほかの三つの分類は、すべてのページで 100 点である。

| ページ | 点数 | FCP | LCP | TBT | CLS |
|---|---:|---:|---:|---:|---:|
| `heavy-code` | 86 | 1.7 秒 | 3.6 秒 | 210 ms | 0 |
| `heavy-math` | 83 | 1.7 秒 | 3.6 秒 | 280 ms | 0.066 |
| `heavy-diagrams` | 85 | 1.5 秒 | 3.6 秒 | 260 ms | 0 |
| `heavy-long` | 84 | 1.5 秒 | 3.6 秒 | 300 ms | 0 |
| `complex-nesting` | 88 | 1.7 秒 | 3.6 秒 | 150 ms | 0 |
| `complex-mixed` | 69 | 1.7 秒 | 3.6 秒 | 830 ms | 0.065 |

図の既定のレイアウトを dagre にする前は、`heavy-diagrams` が 80 点、`complex-mixed` が 65 点だった。

### 見本で分かった、まだ直していない問題

- **TypeScript の色分けが極端に遅い行がある。** `complex-mixed` の約 600 ms の長いタスクは、Shiki による TypeScript のコードブロック一つの色分けだった。関数の引数の中に矢印関数がある行（`Promise.all([a(), b().then((r) => r.c())])`）で、JavaScript の正規表現エンジンでの照合に時間がかかる（手元の Node.js で、同じ行から矢印関数を除くと 0.6 ms、含めると 28 ms）。Shiki の Oniguruma のエンジン（wasm）にすると速くなる見込みがあるが、読み込むものが増える。
- **数式の描画でレイアウトがずれる。** 画面の最初に見えるブロックの数式は、描く前（TeX の文字列）と描いた後で高さが変わり、Cumulative Layout Shift が 0.07 ほどになる。
- **長い記事の最初の描画が長いタスクになる。** `heavy-long` では、本文の Markdown の変換と描画が約 300 ms の長いタスクになる。

## 実装しないこと

- 見本の記事を計測の対象から外すオプション。計測に時間はかかるが、パフォーマンスの基準はまだないので、記録として残す。
- 見本の記事を、ほかの記事と別の DB に分けること。

## テスト設計

- Lighthouse の計測で、見本の記事もユーザー補助とおすすめの方法が 100 点であること（CI）。
- 本体の CSS のファイルが空で残り、`index.html` に中身が埋め込まれること（ビルドの出力で確かめた）。
- 図の既定のレイアウト：ヘッドレスの Chrome で確かめた（上記）。自動のテストにはしていない。

## トレードオフ

- 見本の記事の分だけ、Lighthouse の計測（CI とリリース）が長くなる（8 ページから 14 ページ）。
- 図の見た目が、mermaid 12 の既定（elk）から dagre に戻る。elk で並べたい図には、`layout: elk` を書く必要がある。
- 空の CSS ファイルのために、elk などを読み込むときに小さな要求が一つ増える。
