# 0019 Lighthouse の計測とアクセシビリティ

## 状態

採用。
0017 の「テーマは `github-light`」を置き換える。

## 決定

Lighthouse でサイトのスコアを計測する。
アクセシビリティは 100 点を必須とし、下回れば失敗させる。
パフォーマンス、ベストプラクティス、SEO は計測して記録するだけにし、基準は後で決める。

### 計測の仕組み

`web/scripts/lighthouse.mjs`（`npm --prefix web run lighthouse`）が次を行う。

1. `sqlite-cms serve` で `example/` を配信する。実際に利用者に届くのと同じ、CLI に埋め込んだ SPA を計測するためである。
2. ヘッドレスの Chrome を起動し、代表的な 5 ページを計測する。
   - `/`：トップページ
   - `/articles/syntax`：記法の一覧。コード、表、脚注、折りたたみ、タスクリスト、許可した HTML をすべて含む
   - `/articles/getting-started`：使い方
   - `/posts/ruby`：ルビ
   - `/about`：自己紹介（定義リスト）
3. ページごとに HTML と JSON のレポートを `web/lighthouse-reports/` に書き出す。
4. スコアの表を表示する（CI では実行結果の概要にも書く）。
5. 必須の基準を下回ったページがあれば、足りない項目と該当する要素を表示し、終了コード 1 で終わる。

計測の条件は Lighthouse の既定（モバイル端末、回線と CPU の速度制限を模した計算）とし、1 ページにつき 1 回計測する。

Lighthouse CI（`@lhci/cli`）は使わない。
2025 年 6 月から更新が止まっていて、中の Lighthouse が 12.6 のままだからである（本体は 13.5）。
また、使わない報告用のサーバの依存まで持ち込む。
Lighthouse 本体と `chrome-launcher` を開発者向けの依存として `web/` に入れ、Node の API から直接呼ぶ。

### CI

`ci.yml` のテストの後に計測を実行する。
レポートは、成功しても失敗しても `lighthouse-reports` という Artifact に保存する。失敗したときこそ、原因をレポートで調べる必要があるからである。
GitHub の Ubuntu の実行環境には Chrome が入っているので、追加の準備は要らない。

### 100 点にするための修正

最初の計測では、アクセシビリティが 3 ページで 91〜92 点だった。原因と修正は次のとおり。

- **コードの文字色のコントラスト不足**：`github-light` の文字色は白い背景を前提にしており、背景を本文の `pre` と同じ `#f5f5f5` に置き換えると、赤（`#d73a49`）と緑（`#22863a`）が 4.5:1 を下回った。オレンジ（`#e36209`）は白い背景でも 3.49:1 しかない。テーマを `github-light-high-contrast` に替える。このテーマの文字色は、すべて `#f5f5f5` に対して 4.62:1 以上ある。
- **タスクリストのチェックボックスに名前がない**：GFM のタスクリストのチェックボックスには、読み上げ用の名前が付かない。項目の文章（入れ子のリストの文章は除く）を `aria-label` として付ける。`<label>` で囲む方法は、項目の中に入れ子のリストがあると不正な HTML になるので採らない。
- **脚注の戻りリンクの名前と表示の食い違い**：表示は「↩︎」なのに、読み上げ用の名前が「本文に戻る」で、見えている文字を名前に含んでいなかった。名前を「↩︎ 本文に戻る」にする。

修正後の計測結果（手元の Apple Silicon）は次のとおりである。

| ページ | パフォーマンス | アクセシビリティ | ベストプラクティス | SEO |
|---|---:|---:|---:|---:|
| `/` | 59 | 100 | 96 | 90 |
| `/articles/syntax` | 55 | 100 | 100 | 91 |
| `/articles/getting-started` | 57 | 100 | 100 | 90 |
| `/posts/ruby` | 58 | 100 | 100 | 90 |
| `/about` | 59 | 100 | 100 | 90 |

## 実装しないこと

- パフォーマンス、ベストプラクティス、SEO の基準。値を見てから決める。
- 1 ページにつき複数回計測して中央値を取ること。パフォーマンスの基準を決めるときに、ばらつきを見て検討する。
- `example/` 以外の記事リポジトリの計測。

## テスト設計

- テーマのすべての文字色が、`pre` の背景に対して 4.5:1 以上であること（vitest）。見本の記事に出てこない種類のトークンも含めて守るためである。
- タスクリストのチェックボックスに項目の文章が名前として付き、入れ子の項目にはその項目の文章が付くこと。タスクリストでない項目には付かないこと（vitest）。
- 脚注の戻りリンクの名前が、見えている記号を含むこと（vitest）。
- Lighthouse のスクリプトは、基準を下回ると終了コード 1 で終わり、足りない項目を表示すること。基準を一時的にパフォーマンス 100 点に厳しくして確認した。

## トレードオフ

- 計測に Chrome と、ビルド済みの SPA が要る。CI の実行時間が 1〜2 分延びる。
- 開発者向けの依存が大きく増える（Lighthouse とその依存）。利用者向けのバイナリには含まれない。
- `github-light-high-contrast` は `github-light` より色が濃く、コードの見た目が少し重くなる。
