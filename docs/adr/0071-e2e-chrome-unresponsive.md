# ADR 0071: E2E で Chrome が応えなくなる失敗を、待ち方と再試行で防ぐ

ステータス: 採択

## 文脈

E2E（`web/scripts/e2e.mjs`、[ADR 0044](0044-E2EとCIの最適化.md)）は、場面ごとに Chrome の新しいタブ（`about:blank`）を開き、Chrome DevTools Protocol（CDP、`web/scripts/cdp.mjs`）で動かす。
命令は 30 秒（`COMMAND_TIMEOUT`）で打ち切る。

v0.6.0 の後、CI で次の失敗が 3 回起きた。どれも同じ場面で、同じ形である。

| 実行 | 場面の時間 | 失敗 |
|---|---|---|
| v0.6.1 のリリース（2026-10-12） | 30.6 秒 | Chrome が 30 秒応えない: Runtime.evaluate |
| v0.6.3 の main の CI（2026-10-13） | 30.7 秒 | 同上 |
| PR #10 の CI（2026-10-13） | 30.6 秒 | 同上 |

- 場面は「記事のタグを出し、タグを押すとそのタグの付いた記事だけを探す（[ADR 0048](0048-ハッシュタグ.md)）」。流し直すと通る。
- 場面の時間が、打ち切りの 30 秒とほぼ同じである。場面の最初の命令（新しいタブで `/articles/syntax` を開く `goto`）の中で止まっている。`goto` は `Page.navigate` を送った直後から、`Runtime.evaluate` で本文が描かれたかを確かめ始める。
- `about:blank` から `http://127.0.0.1:…` に移るとき、Chrome は描画のプロセスを替える。`Page.navigate` の応答の直後に送った `Runtime.evaluate` が、捨てられる途中の古い文書に届き、応答が返らないことがあると考えている（Chrome の CDP で知られた振る舞い）。ただし、手元では再現できておらず、確かめられていない。
- 手元で E2E を流し、自動でつないだ iframe と Worker（`Target.setAutoAttach`、`waitForDebuggerOnStart: true`）を調べた。どれも `Runtime.enable` などが成功し、`Runtime.runIfWaitingForDebugger` で動き出していた。ただし、どれかの命令が失敗すると、動き出させる命令を送らない書き方になっている（`Promise.all` の後に送る）。

ブラウザの検査は、[ADR 0070](0070-ci-job-skips-and-required-checks.md) でマージの条件になったので、一時的な失敗でもマージが止まる。

## 実装すること

### ページを移るときは、移り終えてから確かめる

- `goto` は、`Page.navigate` を送った後、そのタブの最上位の文書の `Page.loadEventFired`（読み込みの完了）を受け取るまで待ってから、本文が描かれたかを確かめる。受け取れなければ、30 秒で失敗にする（今と同じ時間）。
- `Page.navigate` の応答に `errorText` があれば、その文字列で失敗にする。

### 待つ間の評価は、短く区切ってやり直す

- `waitFor` の一回ごとの `Runtime.evaluate` を、5 秒で区切る。区切りまでに応答がなければ、その一回は「まだ成り立たない」とみなし、全体の待ち時間（今と同じ、既定 10 秒、場面ごとの指定）までやり直す。
- 全体の待ち時間を過ぎたときの失敗の文言に、応答のなかった回数を書く。
- `waitFor` の外の `eval`（一度だけ評価するもの）は、今までどおり 30 秒で打ち切る。

### 応えなかったときの手がかりを残す

- 命令が打ち切られたときの失敗の文言に、命令の名前だけでなく、`Runtime.evaluate` なら式の先頭（80 文字）と、そのときのタブの URL（`Target.getTargetInfo`。これも応えなければ書かない）を書く。

### 自動でつないだ iframe と Worker を、必ず動き出させる

- `Target.attachedToTarget` を受け取ったら、`Runtime.enable`、`Network.enable`、`Log.enable` の成否にかかわらず、`Runtime.runIfWaitingForDebugger` を送る（`Promise.allSettled` の後に送る）。

### Chrome が応えなかった場面だけ、一度やり直す

- 場面が「Chrome が応えない」（命令の打ち切り）で失敗したときだけ、新しいタブで一度やり直す。ほかの失敗（条件が成り立たない、値が違う）はやり直さない。
- やり直して通った場面は、結果の一覧に「（Chrome が応えず、やり直して通った）」と書き、一回目の失敗の文言も残す。一時的な失敗が続いていることに気付けるようにするためである。
- やり直しても失敗したら、失敗にする。

### 文書

- DEVELOPMENT.md の「E2E」に、待ち方と、やり直す失敗とやり直さない失敗を書く。

## 実装しないこと

- 打ち切りの時間（30 秒）を延ばすこと。止まった命令は、待っても返らない。
- すべての失敗をやり直すこと。表示の誤りを見逃すおそれがある。
- Lighthouse と Core Web Vitals の計測の変更。どちらも、この失敗は起きていない。
- 自動でつなぐこと（`Target.setAutoAttach`）や、`waitForDebuggerOnStart` をやめること。作業用の iframe の中のエラーを集めるのに使っている（[ADR 0055](0055-図を作業用のiframeで描く.md)）。

## テスト設計

`web/scripts/cdp.test.mjs`（node:test、[ADR 0052](0052-ブラウザの検査の並行化.md)）に、偽の CDP のサーバー（WebSocket）を立てて確かめる。

- `goto`：`Page.loadEventFired` を送るまで、`Runtime.evaluate` を送らないこと。`errorText` があれば、その文字列で失敗すること。
- `waitFor`：一回目の `Runtime.evaluate` に応えず、二回目に `true` を返すと、成功すること。ずっと応えなければ、全体の待ち時間で、応答のなかった回数を書いて失敗すること。
- 打ち切りの文言に、式の先頭と URL が入ること。
- `Target.attachedToTarget` で、`Log.enable` が失敗しても、`Runtime.runIfWaitingForDebugger` を送ること。
- 場面のやり直し：「Chrome が応えない」で一度失敗して二回目に通る場面は、やり直したと書いて成功に数えること。条件が成り立たない失敗は、やり直さないこと。二回とも応えなければ失敗すること。（場面を動かす部分を `e2e.mjs` から関数に切り出して確かめる。）
- E2E を手元で通すこと。CI の E2E が通ること。
- その後の CI で、この場面の失敗が減ったか、やり直しの書き込みが出ていないかを見る。

## トレードオフ

- `goto` が読み込みの完了を待つので、ページを開くたびに少し遅くなる（SPA の本文が描かれるのは読み込みの完了の後なので、ほとんど変わらない）。
- 一回ごとの評価を 5 秒で区切るので、本当に 5 秒以上かかる式は、成り立っていても成り立たないとみなされる。待つ間の式は DOM を調べるだけなので、5 秒はかからない。
- 場面を一度やり直すので、Chrome の一時的な不調は隠れる。結果の一覧に書いて、見えるようにする。
- 原因（プロセスの切り替えの間の評価）は推測であり、待ち方を変えても直らないことがある。そのときは、打ち切りの文言に残した式と URL を手がかりに、次の ADR で改める。
