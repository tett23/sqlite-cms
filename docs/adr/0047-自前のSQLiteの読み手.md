# 0047 自前の SQLite の読み手

## 状態

提案。
0002 の「DB ファイルを fetch し、sql.js（wasm）で開く」を、自前の読み手で読む形に改める。
0031 の「FTS4 の索引をブラウザで作って検索する」を、索引を使わずに JavaScript で探す形に改める。
0038 の「index.html で sql.js の wasm を先読みする」をやめる。

## 決定

### SQLite のファイルを自前で読む

0046 の後、残る減点のほとんどは Largest Contentful Paint（3.3 秒）で、本文を描くのに要る取得の大きさで決まっていた。
そのうち 3 分の 2 を sql.js の wasm（gzip 後で約 326 KB）が占めていた。

SPA が DB に問い合わせるのは、表の行をすべて読んで、絞り込むか並べ替えるだけである。
SQLite のファイル形式は公開されている（https://www.sqlite.org/fileformat2.html）。
そこで、表の B-tree とレコードを直接読む小さな読み手を自前で書く（`web/src/sqlite.ts`、約 240 行）。

- ファイルの見出し（ページの大きさ、予約領域、文字の符号化）を読む。UTF-8 以外は扱わない。
- 表の B-tree を、内部のページと葉のページをたどって、rowid の順に読む。大きなレコードは、あふれたページ（overflow）をたどって集める。
- レコードの見出し（可変長の整数）から列の型を読み、NULL、1〜8 バイトの整数、浮動小数点、0 と 1、BLOB、文字列を読む。
- 列の名前は `sqlite_master` の CREATE TABLE 文から取る。`INTEGER PRIMARY KEY` の列は rowid として読む（SQLite と同じく、`INTEGER PRIMARY KEY DESC` は rowid の別名にしない）。
- 列を足す前に入れた行の、足した列は、SQLite と同じくその列の既定値として読む。既定値は定数（文字列、数、16 進の数、NULL、TRUE、FALSE、BLOB）だけを読む。`ALTER TABLE … ADD COLUMN` の既定値は SQLite の決まりで定数に限られるので、足りる。式の既定値を読む必要が出たら、黙って違う値を返さずに失敗する。
- 索引、仮想表、WITHOUT ROWID の表は読まない（sqlite-cms の DB は使わない）。仮想表と WITHOUT ROWID の表を読もうとしたら、読めないことを知らせる。
- ファイルの外のページを指していれば（途中で切れたファイル）、そのことを知らせる。壊れた B-tree で同じページをたどり続けないよう、たどる深さに上限を設ける。

`web/src/db.ts` の関数は、読んだ行を JavaScript で絞り込み、並べ替える。
並べ替えは、SQLite の既定の比べ方（BINARY、UTF-8 のバイトの順）と同じく、コードポイントの順で比べる（`compareBinary`）。

### 検索も自前で行う

全文検索（0031）は、FTS4 の索引で候補を絞った後、JavaScript で「すべての語を含むか」を確かめて結果を決めていた。
語を含む文書は必ず FTS4 の候補にも入るので、索引を使わずにすべての文書を確かめても、結果は同じになる。
記事の数が少ないので、すべての文書を確かめても速い。
検索する文書は、最初に検索したときに一度だけ作る。

これで SPA は SQL を使わなくなり、sql.js を読み込まない。
sql.js は、読み手が SQLite と同じ行を読むことを確かめるテストでだけ使う（開発用の依存に移す）。
ビルドの出力（とバイナリ）から、sql.js の wasm（約 660 KB）と JS がなくなる。

CLI は、index.html で sql.js の wasm を先読みしない（0038 で入れた先読みをやめる）。先読みすると、使わない wasm を本文の前に取得してしまう。

### フッタを最初の画面の外に置く

検索の結果が本文の後から入るようになった検索のページで、すぐ下のフッタが押し下げられ、Cumulative Layout Shift が 0.67 になった（E2E で見つけた）。
本文の領域の高さを、少なくとも画面の高さにする（`min-height: 100vh`）。
フッタが最初の画面の外に来るので、後から入る中身（検索の結果、数式、図）でフッタが押し下げられても、レイアウトのずれにならない。

### 見本の記事

見本の「このブログの仕組み」と、重いページと複雑なページの見本（0040）の、sql.js と wasm を前提にした説明と図を、今の仕組みに合わせて直す。

## 実装しないこと

- SQL の解析と実行。SPA は表の行を読むだけである。
- 索引を使った読み出し。表の行をすべて読んでも、個人のサイトの DB（数百 KB）では十分に速い。
- 書き込み。
- 検索の索引を DB に入れること（0031 と同じく、DB を大きくしない）。

## テスト設計

sql.js を正解として使う。同じ DB を sql.js と自前の読み手で読み、すべての行が一致することを確かめる。

- 乱数で作った 24 の DB（種を決めてあり、毎回同じ）。ページの大きさ（512〜65536 バイト）、auto_vacuum、1〜3 個の表、1〜12 列と各種の列の型、rowid の別名の列のある表とない表、0〜400 行、各種の値（1〜8 バイトの整数の境目の前後、浮動小数点、BLOB、NULL、あふれたページに続く長い文字列、合成文字や絵文字）、負の数や大きな rowid、行の削除と更新、既定値を持つ列の追加、VACUUM を組み合わせる。
- あふれたページの境目：ページの大きさごとに、レコードの大きさを 1 バイトずつ変えてページの 3 倍を超えるまで入れ、ページに収まる上限、あふれる部分の長さの計算の二つの場合分け、あふれたページが 1 枚と 2 枚以上の場合を、すべて通す。
- 20000 行の表（内部のページが何段にもなる）、200 列の表（レコードの見出しが 2 バイトの可変長整数になる）、rowid の端の値（int64 の最小と最大、9 バイトの可変長整数）、NUL を含む文字列（sql.js は NUL で切るので、SQLite の hex() と比べる）。
- 列を足す前の行の既定値（文字列、引用符、符号つきの数、指数、16 進、BLOB、NULL、TRUE、FALSE、空の文字列、制約のある列）。
- 読めない DB（UTF-16、仮想表、WITHOUT ROWID）と壊れた DB（途中で切れたファイル、自分を指す B-tree、表の B-tree でないページ）で、何が起きたかがわかるエラーになること。
- 文字列の比べ方：乱数で作った文字列を、SQLite の `ORDER BY`（BINARY）と同じ順に並べること（NUL を含む文字列は 16 進で書いて比べる）。
- 一覧と取り出し：乱数で作った 30 の DB（同じ日付、日本語の slug を含む）で、`db.ts` の一覧と取り出しが、以前の SQL の問い合わせ（`ORDER BY published_at DESC, slug DESC`、post と article の `UNION ALL`）を sql.js で実行した結果と同じになること。
- CLI：`build_db_bytes` の DB が、読み手の前提（UTF-8、仮想表と WITHOUT ROWID の表がない、既定値が式でない）を守ること。CLI の DB の作り方を変えて前提が崩れたら、このテストが落ちる。

読み手をわざと壊して（あふれる長さの計算、既定値、整数の大きさと符号、可変長整数の符号、`INTEGER PRIMARY KEY DESC`、比べ方）、テストが失敗することを確かめた。

- ページの大きさ（512、1024、4096、65536 バイト）ごとに、300 行（内部のページができる）、あふれたページに続く長い文字列、1〜8 バイトの正と負の整数、浮動小数点、BLOB、NULL、絵文字を含む文字列。
- 表と列の名前を変えた後と、列を足す前に入れた行。
- sqlite-cms のマイグレーションで作った表。
- 表の定義の読み方（引用符、括弧、表の制約、rowid の別名）と、文字列の比べ方（UTF-16 とコードポイントで順が変わる文字）。
- `db.ts` と検索のテストは、sql.js で作った DB を書き出して自前の読み手で開いてから行う。検索の並べ順などの既存のテストがすべて通ることで、FTS4 を外しても結果が変わらないことを確かめた。
- CLI：index.html に DB の先読みを入れ、sql.js の wasm は先読みしないこと。
- E2E：すべてのページ、検索のページ、ヘッダの検索の候補が動くこと。開発サーバー（`npm run dev`、DB のパスをマニフェストから読む）でも動くことを確かめた。

## トレードオフ

- SQLite のファイル形式を読む処理を、自前で持つ。sqlite-cms の DB が使わない形式（索引だけの表、WITHOUT ROWID、UTF-16）には対応しない。CLI が DB の作り方を変えるときは、読み手も確かめる（テストが sql.js と比べる）。
- ブラウザで SQL を使えなくなる。記事の数がとても多いサイトでは、検索のたびにすべての文書を確かめるのが遅くなりうる。
- 短いページでは、フッタが画面の下の外に来る。
