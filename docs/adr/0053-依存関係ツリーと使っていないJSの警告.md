# 0053 依存関係ツリーと使っていない JS の警告

## 状態

提案。
0046 の Worker の形を、数式（KaTeX）にも使う。
0055 で、残した mermaid の警告を、図を作業用の iframe の中で描くことで直した。

## 背景

Lighthouse（と、同じ判定を使う PageSpeed Insights、DevTools のパフォーマンスの分析）で、すべてのページに次の二つの警告が出ていた。

- **ネットワークの依存関係ツリー**（`network-dependency-tree-insight`）：すべてのページで 0 点。
- **使用していない JavaScript の削減**（`unused-javascript`）：本体の JS で、ページによって 21〜26 KiB が使われていない。数式と図のページでは、KaTeX と mermaid のチャンクでも出る。

判定の仕組みを、Lighthouse の分析の実装（`@paulirish/trace_engine` の `NetworkDependencyTree`、`unused-javascript`）で確かめた。

- 依存関係ツリーは、優先度の高い要求が二段以上つながると失敗にする。HTML から `<script type="module">` で読む本体の JS は二段目なので、SPA では必ず失敗する。ただし、先読み（`link rel=preload`、`modulepreload`）で取った要求は数えない。
- 使っていない JS は、スクリプトのファイルごとに、使っていない量（転送量に換算）が 20 KiB を超えたものを挙げる。

本体の JS の使っていない部分を、CDP の正確なカバレッジとソースマップで調べた（`/archive`）。使っていないのは本体の約 52%（生の大きさで約 109 KB）で、ほとんどが Markdown を描く処理（micromark、mdast、hast など）だった。
ヘッダの短い Markdown（`content/header.md`）を描くために、どのページでも Markdown の処理を読み込むが、使う構文は一部だけだからである。記事のページは最初の描画に要るので、後から読み込む形にはできない。

## 決定

- 数式を、Web Worker（`web/src/render/katex.worker.ts`）の中で組む。KaTeX は DOM を使わずに HTML の文字列を作れる。KaTeX の CSS とフォントは、読み込むときにメインスレッドで読む（フォントを待ってから組むのは 0051 と同じ）。Worker の中の JS は、使っていない JS の監査の対象にならない（コードブロックの色分けの Worker（0046）も対象になっていなかった）。数式を組む処理もメインスレッドから外れる。テスト（Node.js）には Worker がないので、同じスレッドで同期的に組む。
- 本体の JS を、index.html の `modulepreload` で先読みする（Vite のプラグイン `modulePreloadEntry`）。取得を始める時刻は変わらない（どちらも HTML を読み始めてすぐに見つかる）。
- Markdown を描くライブラリ（react-markdown、unified、micromark、mdast、hast、remark、rehype とその依存）を、本体と別のチャンク（`markdown`）にする（Rolldown の `advancedChunks`）。本体から静的に読むので、Vite が index.html に `modulepreload` を入れ、本体と並行して取る。

### 結果

- 依存関係ツリーは、すべてのページで合格になった。
- 使っていない JS は、本体（gzip 後 18 KB）と Markdown のチャンク（gzip 後 51 KB）のどちらも 20 KiB を下回り、本体の警告はすべてのページで出なくなった。
- KaTeX の警告は、数式のページで出なくなった。`/articles/heavy-math` の Total Blocking Time は 10 ms だった。
- Core Web Vitals（0050）の LCP は、変える前と変わらなかった（手元で 1.90〜1.99 秒）。
- 警告が残るのは、図のページ（`/articles/heavy-diagrams`、`/articles/complex-mixed`）の mermaid の二つのチャンク（22〜24 KiB）だけである。

本体と Markdown の処理については、使っていない JS の量そのものは減っていない。ファイルを分けて、ファイルごとの基準を下回るようにしただけである。転送量は、要求が二つ（Markdown のチャンクと、Rolldown の小さな実行時のチャンク）増える分、わずかに増える。

## 実装しないこと

- 図のページに残る mermaid の警告。警告の出る二つのファイルは、mermaid が配布の時点で分けているチャンク（`dist/chunks/mermaid.core/chunk-*.mjs`）で、どの種類の図でも使う共通の部分である。一つのモジュールは分けられず、まとめるとファイルごとの量がかえって増える。mermaid は図の文字の大きさを DOM で測るので、Worker にも移せない。図をビルドのときに SVG にするには、CLI がヘッドレスのブラウザで mermaid を動かす必要がある。
- 検索の処理（`search.ts`）を、検索ボックスを使ったときに読み込むこと。描画の中でそのまま使っており、後から読み込む形にする手間に比べて、減るのは 2.5 KB ほどである。
- ヘッダの Markdown を、ビルドのときに HTML にすること。CLI に Markdown の描画（自前の拡張を含む）を持つ必要がある。

## テスト設計

- 手元の Lighthouse で、14 ページの二つの監査の点数と、警告の出るファイルを確かめた。
- Core Web Vitals の計測で、LCP が悪くならないことを確かめた。
- E2E と vitest がそのまま通ること（チャンクの名前に依存するテストはない。数式の E2E は、Worker で組んだ数式を確かめる）。

## トレードオフ

- 本体と Markdown の処理の使っていない JS は、実際には減っていない。Lighthouse の基準（ファイルごとに 20 KiB）に合わせた形である。
- 数式は Worker とのやり取りの分だけ非同期になる。Worker が動かないときは、書き誤りと同じ表示（TeX の文字列と「解釈できませんでした」）になる。
- 本体を変えても、Markdown のチャンクはキャッシュに残る（ライブラリを更新しない限り名前が変わらない）。
- 初めて開くときの要求が二つ増える。
