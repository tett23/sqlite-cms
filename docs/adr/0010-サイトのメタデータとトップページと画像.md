# 0010 サイトのメタデータとトップページと画像

## 状態

採用。
0004 の「トップページの導入の一文は SPA が持つ」と、SPA に直書きしていたサイト名とフッターを置き換える。
仕様書の「画像は静的ファイルとして配信する」の置き場所を、コンテンツリポジトリの側に定める。

## 決定

サイト名などのメタデータは、コンテンツリポジトリのルートの `site.toml` で管理する。
トップページの本文と画像は、コンテンツリポジトリの `content/` 以下で管理する。

```
<コンテンツリポジトリ>/
  site.toml          -- メタデータ（必須）
  content/
    index.md         -- トップページの本文（任意）
    posts/ articles/ pages/
    media/           -- 画像など（任意。/media/ で配信する）
```

### site.toml

```toml
title = "tett23の記事置き場"   # 必須。ヘッダとページタイトルに使う
author = "tett23"              # 任意。フッターに表示する

[license]                      # 任意。フッターに表示する
name = "CC0 1.0"               # [license] を書くなら必須
url = "https://creativecommons.org/publicdomain/zero/1.0/"  # 任意。書けば名前をリンクにする
```

- 知らないキーはエラーにする。綴りの誤り（`licence` など）を黙って無視しないためである。
- `title` と `license.name` は空文字列を認めない。
- `license.url` は `http://` か `https://` で始まるものだけを認める。フッターのリンクになるため、`javascript:` などの URL を入れさせない。

### スキーマ

マイグレーション `0004_site.sql` で、一行だけを持つ `site` テーブルを作る。

```sql
CREATE TABLE site (
  id           INTEGER PRIMARY KEY CHECK (id = 1),
  title        TEXT NOT NULL,
  author       TEXT,
  license_name TEXT,
  license_url  TEXT,
  home_md      TEXT
);
```

キーと値の二列で持つ形ではなく列を固定したのは、項目ごとの必須と任意を DB の制約でも表せるためである。
項目を足すときはマイグレーションで列を加える。

### トップページ

`content/index.md` を frontmatter なしの Markdown として読み、`site.home_md` に加工せず格納する。
SPA はトップページの先頭にこれを描画し、その下に article と post の一覧を自動で並べる。
一覧の見出し（「記事」「ブログ」）と並べ方は SPA が持つ。

### 画像

ビルダーは `content/media/` を配信用ディレクトリの `media/` にそのままコピーし、`/media/` で配信する。

- コピーの前に出力先の `media/` を消す。記事リポジトリで消した画像が配信物に残らない。
- `.` で始まるファイル（`.DS_Store` など）はコピーしない。
- 画像は DB に入れない（仕様書の方針どおり）。
- 記事からは `![説明](/media/foo.png)` のように参照する。

### SPA

- ヘッダのサイト名、ページタイトル、フッターは `site` テーブルから読む。サイト名の直書きをなくす。
- フッターは `author` と `license` のどちらかがあるときだけ表示する。
- `index.html` の `<title>` は空にし、DB の読み込み後に設定する。

## 実装しないこと

- 画像ファイル名のハッシュ化と `immutable` キャッシュ。画像はブラウザの通常のキャッシュに任せる。
- 画像の最適化（リサイズ、形式変換）。多用する段になったら CDN の画像最適化に載せる。
- `site.toml` のその他の項目（説明文、言語、ナビゲーションの項目など）。必要になった時点で列を足す。
- DB の読み込み前のページタイトル。SEO を考慮しないため、読み込みまでの短い間は空のままとする。

## テスト設計

`cargo test` で次を検証する。

- `site.toml` の解釈（全項目、任意項目の省略、`title` の欠落と空、知らないキー、壊れた TOML、`license` の `url` の省略、`name` の欠落、`http(s)` 以外の `url`）。
- `site` テーブルに `site.toml` と `index.md` の内容が入ること、`index.md` がなければ `home_md` が NULL になること、`site.toml` がなければビルドが失敗すること。
- `media/` のコピー（入れ子のディレクトリ、ドットファイルの除外、前回のビルドの残骸の削除、元がないときに出力が残らないこと）。

vitest で、`getSite` がライセンスの有無に応じた値を返すことを検証する。
ヘッダ、フッター、トップページの本文、画像の表示、ページタイトルはブラウザで確認する。

## トレードオフ

- 画像は DB と違ってファイル名にハッシュを持たないので、配信の差し替えは原子的ではない。デプロイの途中では、新しい DB が古い画像を参照する瞬間がありうる。画像は差し替えより追加が多く、同じ名前で中身を変えない運用なら問題にならない。
- メタデータの項目を増やすたびにマイグレーションが要る。キーと値の形にすれば不要だが、必須と任意の区別が DB から消える。
