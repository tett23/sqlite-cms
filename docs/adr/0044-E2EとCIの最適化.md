# 0044 E2E のテストと CI の最適化

## 状態

提案。
0019 の Lighthouse の計測を、並行して行えるようにする。
0045 で、E2E のレイアウトのずれを確かめる対象から、図の多い記事を外した（図を描くときにもずれる）。

## 決定

### 単体テストの充実

カバレッジを一時的に計測し（`@vitest/coverage-v8` を保存せずに入れて計測し、外した）、ブラウザの API に触れるところが手薄だとわかった（行の網羅率で、`documentMeta.ts` 14%、`lazyLoader.ts` 45%、`nearViewport.ts` 42%、`router.tsx` 58%、`db.ts` 67%。`App.tsx` はどのテストからも読み込まれていなかった）。
jsdom などの DOM の代わりになるライブラリは入れず（依存の方針）、差し替えられるところは差し替えて単体テストにする。

- `loadDb`：`sql.js` をモックし、`fetch` と `document` を差し替えて、index.html の DB のパスを使うこと、取れないときと通信の失敗のときにマニフェストから読み直すこと、失敗の知らせ方を確かめる。
- `documentMeta`：小さな偽の `document` で、meta description を作ることと書き換えることを確かめる。
- `inTurn` と `whenIdle`：偽のタイマーと、差し替えた `requestAnimationFrame`、`requestIdleCallback` で、呼ぶ順と、どの段階で取り消しても呼ばないことを確かめる。
- `navigate` と `Link`：偽の `window` で、履歴の足し方と置き換え方、押したときに読み直さずに移ることと、修飾キーや新しいタブではブラウザに任せることを確かめる。
- `header.rs`：site.toml の値の組み立て（url の末尾の `/`、description の既定、値がないとき）を確かめる。

足したテストのいくつかは、実装をわざと壊して失敗することを確かめた（取り消しでタイマーを止めない、一つずつではなく続けて呼ぶ）。

### E2E のテスト

描画を伴う動きは、ヘッドレスの Chrome で確かめる（`web/scripts/e2e.mjs`、`npm run e2e`）。
依存を足さず、Lighthouse の計測で使っている chrome-launcher で Chrome を起動し、Chrome DevTools Protocol を WebSocket で直接使う。
これまで手元で都度書いていた確認のスクリプトを、CI で動くテストにまとめたものである。

| 確かめること | 関係する ADR |
|---|---|
| 計測するすべてのページが、コンソールのエラーと 400 以上の応答なく描かれ、レイアウトがずれない（数式でずれる既知の 2 ページを除く） | 0038、0040、0043 |
| 画面の外のコードブロックは、近くに来てから色を付ける。コードのないページでは Shiki を読まない | 0029、0038 |
| 色分け、数式、図を描き、書き誤りのある数式と図だけを元の文字列のまま出す | 0017、0025 |
| elk は、図で指定したときだけ読み込む | 0040 |
| リンクで、ページを読み直さずに移り、戻れる | 0002 |
| ヘッダの検索ボックスで、候補を 5 件まで出し、キーで選んで移れる。一致しないときにその旨を出し、Escape で閉じる | 0042 |
| 検索のページは、URL の言葉で結果を出し、ヘッダから探すと結果が変わり、戻ると元に戻る | 0031、0042 |
| 知らないページは「見つかりません」を出す | 0002 |
| content/header.md のヘッダを描き、なければ既定のヘッダを描く | 0043 |
| サイトをドメインの直下でない場所（base_path）に置いても、本文、移動、検索、画像が動く | 0030 |

- 既定のヘッダと base_path は、`example/` の写しを一時ディレクトリに作って配信する（`content/header.md` を除いたものと、`base_path = "/blog/"` を足したもの）。認証情報（`.env`）は写さない。
- ページやライブラリを待つときは、決まった時間だけ待たずに、条件が成り立つまで待つ（`waitFor`）。遅いマシンで失敗しないためである。
- Chrome に送る一つの命令は 30 秒、一つのシナリオは 120 秒で打ち切る。Chrome が応えなくなったときに、CI のジョブの制限時間まで待ち続けないためである。
- `E2E_CPU_THROTTLE` で CPU を遅くして動かせる。手元より遅い CI のマシンで待ち時間が足りるかを、手元で確かめるためである。

E2E が本当に不具合を捕まえるかを、直した不具合を戻して確かめた。

- 本体の CSS のファイルを消す（0040 で直した 404）と、「エラーなく描かれる」と「図を描く」が失敗した。このとき、elk の図のあるページでは図が一つも描かれなかった。CSS の読み込みの失敗で、mermaid の動的な import 自体が失敗するためである。0040 で直す前は、本番でもこうなっていた。
- mermaid の既定のレイアウトを elk に戻すと、「elk は、図で指定したときだけ読み込む」が失敗した。

E2E を書く中で、次の不具合を見つけて直した。

- **広い画面のトップページで、レイアウトがずれる**（0.005）。カスタムのヘッダ（0043）では、DB を読むまで読み込み中の表示だけを描くが、DB を読んだときに Preact が同じ `div` を使い回してクラスだけを書き換えたので、要素が動いたと数えられた。読み込み中の表示と本文の側で `key` を変え、置き換えるようにした。Lighthouse はスマートフォンの幅で計測するので、見つからなかった。

### Lighthouse の並行した計測

`LIGHTHOUSE_CONCURRENCY` に 2 以上を渡すと、ページを分けて、その数の子プロセスで計測する。
Lighthouse は一つのプロセスの中で並行して動かせないので、子プロセスごとに別の Chrome を使う。
重いページが一つの子プロセスに偏らないよう、ページを順に配る。
子プロセスは結果をファイルに書き、親がページの順に並べ直して、今までと同じ表と判定を出す。

手元（Apple Silicon）で、14 ページの計測は 1 つずつで 89 秒、3 つ並行で 38 秒だった。
アクセシビリティ、おすすめの方法、SEO の点数は変わらなかった。
パフォーマンスの点数は、多くのページで 0〜2 点の差だったが、一つのページで 8 点下がった（CPU を取り合うため）。
パフォーマンスは記録するだけで合否に使わないので、CI では 3 つ並行で計測する。手元の既定は 1 のままにし、パフォーマンスを比べるときは 1 で計測する。
並行して計測しても、アクセシビリティの違反で失敗することを、ヘッダの検索欄のラベルを外して確かめた。

### CI の構成

CI（`ci.yml`）は一つのジョブのままにし、速く終わる検査から順に行う。SPA のビルドと vitest、clippy と `cargo test`、E2E、Lighthouse の順である。

- ジョブを分けて並行して動かすことも考えた。しかし Rust の結合テストは埋め込んだ SPA を使うので、SPA のビルドのジョブを待ち、成果物を受け渡す必要がある。ジョブごとのセットアップ（npm ci とキャッシュの復元で 20 秒ほど）も重なり、一つのジョブより遅くなる見込みだったので採らない。
- E2E と Lighthouse は、`cargo test` が作った `target/debug/sqlite-cms` で配信する（`SQLITE_CMS_BIN`）。`cargo run` での組み立て直しの確認を省く。
- `docs/`、`README.md`、`DEVELOPMENT.md` だけを変えたときは動かさない（`paths`）。見本の記事（`example/` の Markdown）は計測とテストに使うので、除かない。

リリース（`release.yml`）は次のように変える。

- `cargo test --release` を `--target` 付きで行い、続く `cargo build --release --target` でそのまま使う。これまではテストとビルドの出力先が違い、同じものを二度コンパイルしていた。手元では、テストの後のビルドが 0.07 秒で終わることを確かめた（これまでは、ここで二度目のコンパイルがあった）。
- Rust のキャッシュ（`Swatinem/rust-cache`）を使う。
- Linux のビルドで E2E を行い、Lighthouse を 3 つ並行で計測する。

## 実装しないこと

- jsdom、happy-dom、Playwright などの依存を足すこと。
- カバレッジの計測を CI に入れること（`@vitest/coverage-v8` の依存が増える）。今回は一時的に計測しただけである。Rust のカバレッジ（`cargo llvm-cov`）も、ツールを入れる必要があるので計測していない。
- E2E を複数のブラウザで動かすこと。
- パフォーマンスの点数に基準を設けること。

## テスト設計

- E2E の各シナリオは、上の表のとおり。
- 直した不具合を戻し、E2E が失敗することを確かめた（上記）。
- E2E を続けて何度か動かし、また CPU を 4 倍遅くして動かし、結果が揺れないことを確かめた。
- Lighthouse の並行した計測で、すべてのページのレポートが出ること、作業用のファイルが残らないこと、アクセシビリティの違反で失敗することを確かめた。

## トレードオフ

- CI の Lighthouse のパフォーマンスの点数は、並行して計測する分だけ揺れる。
- E2E の分だけ CI が長くなる（手元で約 30 秒）。Lighthouse の並行化で縮んだ時間（手元で約 50 秒）の中に収まる。
- E2E は見本（`example/`）の記事の数や内容（コードブロックの数、図の数など）に依存する。見本を変えたら、E2E の期待値も直す。
- ワークフローの変更は、GitHub Actions で実際には動かしていない（手元に act や actionlint がなく、push していない）。
