# 0062 開発サーバーの DB の書き出し直し

## 状態

提案。

## 決定

Vite の開発サーバー（`npm --prefix web run dev`）で、DB が消えていたり古くなっていたりしたら、自動で書き出し直す（`web/dev/devDatabase.ts`）。

開発サーバーは、起動のときに `sqlite-cms build --data-only` で `web/public/db` に DB を書き出し、それを配る。
動かしている途中で `web/public` を消したり、マイグレーションを足して DB の形が古くなったりすると、SPA が DB を読めなくなっていた。
本番のビルド、`serve`、`deploy` は、毎回すべてのマイグレーションを当てて DB を作るので、この問題はない。

- 確かめるとき：開発サーバーの起動のときと、`/db/` への要求のたび。
- 確かめること：DB の案内（`db/manifest.json`）と、案内が指す DB があるか。DB に記録された適用済みのマイグレーション（`schema_migrations`）の最新の版が、`migrations/` の最新の版より古くないか。案内や DB を読めないときも、書き出し直す。
- 書き出し直し：`npm run data`（`sqlite-cms build --data-only`）を動かす。`SITE_DIR` の指定は、環境変数をそのまま引き継ぐ。書き出しは、毎回すべてのマイグレーションを当てて DB を作るので、最新の形になる。書き出し終わるまで、要求を待たせる。
- DB は、SPA と同じ自前の SQLite の読み手（`web/src/sqlite.ts`、0047）で読む。
- 理由（「DB の案内がありません」、「DB のマイグレーションが古くなっています（0010。最新は 0011）」など）を、開発サーバーの出力に出す。
- vitest も Vite を開発サーバーと同じ形で動かすが、テストでは使わない（`VITEST` の環境変数と、`test` のモードで外す）。CI で、テストのたびに DB を書き出さないためである。
- 部品は SPA のコード（`web/src/`）の外の `web/dev/` に置く。Node の機能を使うためである。

## 実装しないこと

- 記事（`content/`）が変わったときの書き出し直し。完成形の確認は、記事の変更を自動で反映する `sqlite-cms serve`（0034）を使う。
- 本番のビルド、`serve`、`deploy` の変更。毎回 DB を作り直しているので要らない。

## テスト設計

- `staleReason`（vitest）：DB が最新なら書き出し直さないこと。案内がない、DB がない、マイグレーションが増えた、記録がない、案内や DB が壊れているときに、理由を返すこと。
- プラグイン（vitest）：起動のときと、`/db/` への要求のときだけ確かめ、古ければ書き出し直すこと。新しければ書き出し直さないこと。テストのモードとビルドでは使わないこと。
- 手で確かめたこと：開発サーバーを動かしたまま、`web/public/db` を消して `/db/manifest.json` を開くと、書き出し直されて、最新のマイグレーションまで記録された DB が返ること。DB の記録から最新のマイグレーションを消すと、書き出し直されること。書き出し直した後にページが描かれること。

## トレードオフ

- 書き出し直すあいだ（Rust の CLI のビルドを含む）、開発サーバーは応えない。
- `/db/` への要求のたびに DB を読む（開発サーバーだけ。DB は小さい）。
