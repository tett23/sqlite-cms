# 0046 メインスレッドを空ける

## 状態

提案。
0017 の「JavaScript の正規表現エンジンで、ハイライタを同期的に作る」を、Oniguruma（wasm）のエンジンと Web Worker に改める。
0018 の「本文の HTML を rehype-raw で取り込む」を、自前の rehype のプラグインに改める。
0038 の「コードブロックを一つずつ、メインスレッドで色分けする」を、Web Worker での色分けに改める。

## 決定

Lighthouse の Total Blocking Time と、本体の JS の大きさを減らすため、次の三つを行う。

### 1. コードの色分けを Oniguruma（wasm）で、Web Worker の中で行う

計測すると、コードのあるページの Total Blocking Time のほとんどは Shiki の色分けだった。
JavaScript の正規表現エンジンでは、文法の正規表現を JavaScript の正規表現に変換する手間（4 倍に遅くした CPU で約 110 ms）と、変換した正規表現の照合が重かった。
TypeScript の文法は特に重く、関数の引数の中に矢印関数がある一行で、数百ミリ秒かかった（0040 に記録した問題）。

- 正規表現エンジンを Oniguruma（`shiki/engine/oniguruma`、wasm）にする。変換がなくなり、照合も速くなる。wasm（gzip 後で約 160 KB）は `shiki/onig.wasm` のファイルとして、色分けを始めるときに取得する。依存は増えない（`shiki` の依存に含まれている）。0017 で JavaScript のエンジンを選んだのは、rehype のプラグインとして同期的に色分けするためだったが、0038 で色分けを部品ごとの非同期の処理にしたので、この制約はなくなっていた。
- Oniguruma にしても、TypeScript の文法の正規表現のコンパイルに、一行目で約 300 ms（4 倍に遅くした CPU）かかった。そこで、色分けを Web Worker（`web/src/highlight.worker.ts`）の中で行う。Total Blocking Time はメインスレッドの長いタスクだけを数えるので、色分けにどれだけかかっても入らない。メインスレッドは、届いた HTML を入れるだけになる。
- テスト（Node.js）には Worker がないので、同じスレッドで同期的に色分けする。テストでは wasm を埋め込んだモジュール（`shiki/wasm`）を使う。この分岐はビルドでは消え、ビルドの出力に入らないことを確かめた。
- Worker は ES モジュールとして出力する（`worker.format`）。Worker の中の wasm の URL は Worker の場所からの相対になるので、サイトをドメインの直下でない場所（0030）に置いても動く（E2E で確かめた）。

### 2. 数式を一つずつ組む

KaTeX を読み込み終わったときに、画面の近くにある数式をまとめて一度に組んでいたので、数式の多いページで長いタスクになっていた。
コードブロック（0038）と同じく、数式ごとに別のタスクで組む（`inTurn`）。一つの数式は短いので、Worker は使わない。

### 3. 本文の HTML を自前のプラグインで取り込む

rehype-raw は HTML パーサ（parse5）を持ち込み、本体の JS（gzip 後で約 134 KB）のうち約 52 KB を占めていた。
0018 は、後から読み込むと `<details>` の中身が見えてから折りたたまれるので、後から読み込む形は採らなかった。
そこで、読み込む時期は変えず、取り込み方を自前で書く（`web/src/markdown/rawHtml.ts`）。

- raw のノードを、開始タグ、終了タグ、文字に分ける。注釈、doctype、CDATA は捨てる。`script` や `style` などの中はタグとして読まない。
- 兄弟のノードを順に見て、開いている要素を積み上げ、その後のノードを子にする。`<details>` の開始と終了の間に Markdown の段落を挟む書き方も、一つの要素にまとまる。閉じていない要素は親の終わりで閉じ、開いていない要素の終了タグは捨てる。
- 要素の属性は `hastscript` で hast のプロパティにし、文字参照は `decode-named-character-reference` で文字にする。どちらも micromark や rehype-raw が使っていてバンドルに入っていたもので、直接の依存として明示するだけである。
- HTML の仕様どおりの解析（暗黙の閉じ、要素の組み替えなど）はしない。取り込んだ後に必ず rehype-sanitize を通すので、崩れた HTML を仕様と違う形に取り込んでも、許可しない要素と属性は残らない。

本体の JS は gzip 後で約 134 KB から約 85 KB になった。

### 計測結果

Lighthouse のパフォーマンス（手元の Apple Silicon、`serve` で配信、1 つずつ計測）。

| ページ | 前 | Oniguruma | Worker | 自前の取り込みと数式 |
|---|---:|---:|---:|---:|
| `/articles/getting-started` | 83 | 88 | 89 | 92 |
| `/posts/ruby` | 84 | 88 | 90 | 92 |
| `/articles/heavy-math` | 84 | 84 | 84 | 92 |
| `/articles/complex-mixed` | 69 | 73 | 86 | 90 |
| `/` | 88 | 87 | 88 | 90 |

`/articles/complex-mixed` の Total Blocking Time は 850 ms から 160 ms に、`/articles/heavy-math` は 290 ms から 80 ms になった。
本体の JS が小さくなったので、First Contentful Paint は 1.7 秒から 1.2 秒に、Largest Contentful Paint は 3.6 秒から 3.3 秒になった。
続く 0047 で、Largest Contentful Paint はさらに縮む。

## 実装しないこと

- 数式を Worker で組むこと。一つずつなら短い。
- 図（mermaid）を Worker で描くこと。mermaid は DOM を使う。
- Markdown の解析を Worker で行うこと。本文を描く前に Worker の読み込みを待つことになり、Largest Contentful Paint が遅れる。長い記事（`/articles/heavy-long`）では、解析が約 200 ms の長いタスクとして残る。
- HTML の仕様どおりの解析。

## テスト設計

- 色分け：登録したすべての言語を Oniguruma のエンジンで色分けできること（既存のテスト）。
- HTML の取り込み：字句への分け方（属性の書き方、大文字、注釈、`script` の中、タグでない `<`、閉じていないタグ）、文字参照、段落をまたぐ要素、段落の中の要素、入れ子、閉じていない要素と開いていない終了タグ、取り込んだ後の無害化。既存の無害化のテスト（`script` を中身ごと消す、イベント属性と `javascript:` のリンクを消すなど）もすべて通ること。
- E2E：色分けが Worker で動き、コードのないページでは Worker を起動しないこと（Worker のスクリプトの取得で見る。Worker の中からの通信はページの側からは見えない）。
- 開発サーバー（`npm run dev`）でも、色分け、数式、図、検索が動くことを確かめた。

## トレードオフ

- コードのあるページで、wasm（gzip 後で約 160 KB）を余分に取得する。本文を描いた後に取得するので、表示の速さの見積もりには入らない。
- 色分けの結果が届くまで、Worker とのやり取りの分だけ遅れる。
- 自前の HTML の取り込みは、ブラウザと違う形に取り込むことがある（崩れた HTML、暗黙の閉じ）。本文に書く HTML は 0018 で許可した少数のタグなので、実際に困ることは少ないと考える。
