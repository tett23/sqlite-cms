# 0050 Core Web Vitals の計測

## 状態

提案。
0019 の「パフォーマンスは計測して記録するだけ」に、Core Web Vitals の基準を足す。アクセシビリティとベストプラクティスの 100 点の基準（0019、0024）は変えない。

## 決定

Lighthouse と同じページ（`web/scripts/pages.mjs` の `PAGES`）で Core Web Vitals（LCP、INP、CLS）を計測し、どれかのページで「良好」の上限を超えたら、計測のスクリプトを失敗させる（`web/scripts/web-vitals.mjs`）。
CI（`ci.yml`）と、リリースのビルド（`release.yml`、0021）で、Lighthouse の後に実行する。失敗すれば CI も失敗し、Release は作られない。

| 指標 | 上限 |
|---|---:|
| LCP | 2.5 秒 |
| INP | 200 ms |
| CLS | 0.1 |

### Lighthouse ではなく自前で計測する

Lighthouse の通常の計測（navigation）は、ページを開くだけで操作をしないので、INP を測れない。
Lighthouse の操作の計測（user flow）は Puppeteer を要する。依存を足さないよう、E2E（0044）と同じく、Chrome DevTools Protocol で Chrome を直接動かして計測する。
E2E のブラウザの操作（`Tab`）は、共通の `web/scripts/cdp.mjs` に移す。

### 計測の条件と手順

条件は Lighthouse のスマートフォンの計測（0019）と同じにし、点数と比べられるようにする。

- 画面は 412 × 823（端末のピクセル比 1.75）。
- CPU を 4 倍遅くする。通信は、Lighthouse が DevTools で絞るときの遅い 4G（往復の遅延 562.5 ms、下り 1.47 Mbps、上り 675 Kbps）にする。キャッシュは使わない。
- ページを開く前に、`PerformanceObserver` で `largest-contentful-paint`、`layout-shift`、`event` の記録を集めるスクリプトを入れる。
- ページを開いて 2 秒待ち（色分け、数式、図を描き終わるまで）、LCP を読む。LCP は最初の入力で決まるので、操作の前に読む。
- 操作：ヘッダの検索ボックスを押し、「sql」を一文字ずつ打ち（打つたびに候補を描き直す）、Escape で閉じ、ヘッダの「一覧」を押してページを移る。どのページにもあり、本体の描画（Preact）を動かす操作である。入力は本物の入力（CDP の `Input`）で送る。合成のイベント（`dispatchEvent`）は INP に数えられない。
- CPU を取り合うと INP が揺れるので、ページは一つずつ計測する。

### 値の計算

値は、Chrome の定義と `web-vitals` ライブラリの数え方に合わせる（`web/scripts/vitals.mjs`）。

- LCP：最後の `largest-contentful-paint` の時刻。
- CLS：直前の入力によらないずれを、間が 1 秒未満、全体が 5 秒以内のまとまりに分け、合計の最も大きいまとまり。
- INP：操作（`interactionId`）ごとに最も長い時間を取り、操作 50 回ごとに長いものを一つ除いた最大（98 パーセンタイルの近似）。

### 結果

手元（Apple Silicon）で 2 回計測した。すべてのページが「良好」だった。

| | 最も悪いページ | 値 |
|---|---|---:|
| LCP | `/articles/heavy-long` | 2.20〜2.24 秒 |
| INP | 数ページ | 56 ms |
| CLS | `/articles/complex-mixed` | 0.017 |

14 ページで 81 秒かかる。

## 実装しないこと

- `web-vitals` ライブラリや Puppeteer の依存。値の計算は数十行で、テストで確かめる。
- 本番（Cloudflare）での実際の利用者の計測（RUM）。計測用の通信と保存先が要る。
- 広い画面での計測。基準はスマートフォンの条件で判定する。
- FCP や TBT など、Core Web Vitals 以外の指標の基準。Lighthouse のパフォーマンスの点数として記録する（0019）。

## テスト設計

- 値の計算（vitest）：LCP は最後の記録を使うこと。CLS は直前の入力によるずれを除き、1 秒の間と 5 秒の幅でまとまりを分けて、最大を取ること。INP は操作ごとに最も長い時間を使い、操作がないときは値なしにし、50 回ごとに一つ除くこと。値なしか上限を超えたものを失敗にすること。
- INP：ヘッダの検索ボックスの入力の処理に、一時的に 250 ms 動き続ける処理を足して計測し、全ページで INP が 296〜312 ms になって、終了コード 1 で終わることを確認した。
- CLS：ページを開いて 1.5 秒後に、本文の前に高さ 400 px の要素を足す処理を一時的に入れて計測し、CLS が 0.486 になったページで、終了コード 1 で終わることを確認した（足す前に描かれていなかったページは、ずれにならなかった）。
- E2E は、`cdp.mjs` に移した後も同じシナリオが通ること。

## トレードオフ

- CI が 1 分半ほど長くなる。
- LCP の余裕は 0.3〜0.6 秒しかない。CI の機械が手元より遅いと、LCP で失敗することがある。CPU を遅くする倍率は `WEB_VITALS_CPU_THROTTLE` で変えられるが、CI では変えず、失敗したら原因を調べる。
- 実際の利用者の値ではなく、決まった条件での実験室の値である。操作も 1 種類だけなので、ほかの操作の遅さは捕まえない。
