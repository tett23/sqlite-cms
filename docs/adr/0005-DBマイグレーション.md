# 0005 DB マイグレーション

## 状態

採用。0001 の「スキーマをビルドスクリプトにインラインで持つ」方式を置き換える。

## 決定

スキーマを連番 SQL ファイルの適用列として定義する。

- マイグレーションは `migrations/NNNN_名前.sql` に置く。ファイル名昇順に適用する。
- 適用記録は `schema_migrations (version TEXT PRIMARY KEY, name TEXT NOT NULL)` に残す。ビルド成果物の決定性を保つため、適用時刻は記録しない。
- ビルドスクリプトは空の DB に全マイグレーションを適用してからコンテンツを挿入する。
- 適用関数 `applyMigrations` は `schema_migrations` を見て適用済みの version をスキップする。ビルドでは常に空 DB から全件適用になるが、既存 DB に追い付かせる用途（ローカルの実験など）でも同じ関数が使えるようにしておく。

DB はビルドごとに作り直す成果物であり、本番のデータを migrate する場面はない。
それでもマイグレーション形式を採るのは、スキーマの変更履歴を差分として残し、変更のたびにフロントエンドのクエリとどちらが先行しているかを付き合わせられるようにするためである。

### 初期マイグレーション

- `0001_initial.sql`：旧スキーマ（`articles` 単一テーブル）。
- `0002_content_types.sql`：`articles` を `posts` に改名し、article 用の新 `articles` テーブルと `pages` テーブルを作る（ADR 0004）。

0001 を現行スキーマに書き直さず改名の差分として残すのは、履歴を実際の変更順に一致させるためである。

## 実装しないこと

- down マイグレーション。DB は使い捨ての成果物であり、巻き戻しはマイグレーションファイルの削除で足りる。
- データ変換を伴うマイグレーション（SQL 以外のスクリプト実行）。必要になった時点で ADR を追加する。

## テスト設計

- 空 DB への全件適用後、`schema_migrations` に全 version が記録されることを検証する。
- 一部適用済みの DB に対して、未適用分だけが適用されることを検証する。
- 適用順がファイル名昇順であることを検証する。

## トレードオフ

- ビルドのたびに全マイグレーションを再生するため、マイグレーションが積もるとビルドがわずかに遅くなる。記事数百件・マイグレーション数十件の規模では測定可能な差にならない。
