# 0051 Core Web Vitals の改善

## 状態

提案。
0038 で試して採らなかった「GFM の解析だけを登録する自前のプラグイン」を採る。Core Web Vitals の基準（0050）で、LCP の余裕を増やすためである。
0040、0044 の「数式は、描く前と描いた後で高さが変わる」を、高さの見積もりで小さくする。
v0.1.5 の CI で、`/articles/heavy-long` の LCP は 2.75 秒から 2.09 秒になり、最も悪いページは `/articles/complex-nesting` の 2.14 秒だった（見込みどおり）。

## 背景

v0.1.4 の CI で、Core Web Vitals の計測（0050）が `/articles/heavy-long` の LCP 2.75 秒（上限 2.5 秒）で失敗した。
手元では 2.20 秒で、CI の機械は CPU が遅いので、CPU を使う処理の多いページほど差が開く（ほかのページは手元より 0.1〜0.2 秒遅いだけだった）。
Lighthouse では、ほかに次の警告が出ていた。

- 本文の画像に `width` と `height` がない（`unsized-images`）。
- 数式を組むときと、KaTeX のフォントが届いたときに、本文がずれる（CLS。`/articles/complex-mixed` で 0.044）。
- 長い記事で長いタスク（210 ms）があり、Total Blocking Time が 210 ms。

## 決定

### 長い本文を少しずつ描く

長い記事の最初の描画までの時間を、CPU のプロファイルで調べた。
JS の到着（1.74 秒）から LCP（2.13 秒）までの 0.39 秒のほとんどが、本文全体の Markdown の解析と、全体の要素の作成と配置だった。
本文全体の解析は、手元の機械で約 30 ms（計測の条件の CPU 4 倍の遅さで約 120 ms）かかる。

そこで、記事、ページ、トップページの本文（`MarkdownBody` の `progressive`）を、次のように描く。

1. 最初の画面には、本文の先頭の部分（`web/src/markdown/firstPart.ts`）だけを解析し、その先頭の 24 個の要素（ブロックの間の改行を含む）だけを描く。
2. 画面に出た後（`requestAnimationFrame` の後のタスク）に、全体を解析して、48 個ずつ、別のタスクで描き足す。

先頭の部分は、先頭の部分を描いた結果が、全体を描いた結果の先頭と同じになるところでだけ切る。

- 2,000 字目以降で、空行の後の、列の先頭から始まる見出しの直前で切る。見出しは、リスト、引用、表、段落を終わらせ、遅延継続にもならない。
- コードのフェンス、`$$` の数式、`:::` の中、空行で終わらない HTML のブロック（`<pre>`、コメントなど）の中では切らない。
- 後ろにあるリンクの参照の定義と脚注の定義は、一行で前後が空行のものに限り、先頭の部分の後ろに足す。脚注の番号は参照の順に付くので、先頭の部分の番号は全体と同じになる。それ以外の形の定義（複数行の脚注、リストや引用の中の定義）が後ろにあれば、切らずに全体を描く。
- 先頭の部分に足した定義で出る脚注の欄は描かない。全体を描くと本文の最後に移り、画面に出ていればずれになる。

要素の key は、親の中での要素の名前ごとの順番なので、先頭の部分の要素と全体の要素の key は同じになり、描き足すときに作り直さない。
見本のすべての記事で、先頭の部分を描いた結果が、全体を描いた結果の先頭と一致することをテストで確かめる。

### 本体の JS を小さくする

LCP は、JS（gzip 後で約 73 KB）の到着でほぼ決まっている（DB は 37 KB で先に届く）。遅い 4G では 1 KB が約 5.4 ms に当たる。

- remark-gfm をやめ、GFM の解析だけを登録する自前のプラグイン（`web/src/markdown/gfm.ts`）にする。remark-gfm は Markdown への書き出しの拡張も登録するので、使わない `mdast-util-to-markdown` と `markdown-table` が本体に入っていた。依存は `micromark-extension-gfm` と `mdast-util-gfm`（どちらも remark-gfm が使っていたもの）に替わる。
- `@ungap/structured-clone`（mdast-util-to-hast と hast-util-sanitize が使う互換の実装）を、ブラウザの `structuredClone` を呼ぶだけのものに置き換える（Vite の別名）。対応するブラウザはすべて `structuredClone` を持つ。

本体の JS は、gzip 後で 74.3 KB から 69.0 KB になった。すべてのページの LCP が 30〜40 ms 縮んだ。

### 本文の画像に大きさを付ける

CLI が組み立てるときに、`content/media/` の画像の大きさを読み、DB の `media_sizes`（マイグレーション 0009）に入れる（`cli/src/media.rs`）。

- PNG、JPEG、GIF、WebP は、`image` のヘッダの読み込みで大きさを得る（画像全体は展開しない）。
- SVG は、ルートの要素の `width` と `height`（単位なしか px）、なければ `viewBox` の幅と高さを使う。% や em は使えないので、大きさなしにする。
- 大きさの分からないファイルは入れない。

SPA は、本文の画像のパスが表にあれば、`img` に `width` と `height` を付ける。`=160x` で幅だけを指定したときは、縦横比を保つ高さにする。CSS で `height: auto` にし、幅を縮めたときも縦横比を保つ。

### 数式の場所を取っておく

数式は KaTeX を読み込むまで TeX の文字列を表示し、組んだときに高さが変わる（ブロックの数式は 24〜48 px が 57〜170 px になる）。

- ブロックの数式は、組む前に、組んだ後の高さの見積もりを `min-height` にする（`displayMathHeight`）。上下の余白 2rem と、行ごとに、分数や総和などがあれば 2.9rem、なければ 1.75rem。行は、`aligned` や `cases` など行を分ける環境の中の `\\` で数える。見本の数式で、組んだ高さとの差は 0.6rem ほどだった。
- 文中の数式は、文中でも大きく組む記法（`\dfrac`、`\dbinom`、`\displaystyle`）だけ、組む前の行の高さを 2.5 にする。文中の `\frac` や `\sum` は小さく組むので、行の高さに収まる。
- KaTeX の CSS は、フォントを読み終わるまで文字を描かない（`font-display: block`）。組んだ後にフォントが届くと、数式の大きさが変わって本文がずれた（`/articles/complex-mixed` で 0.027）。KaTeX を読み込むときに、よく使うフォント（KaTeX_Main と KaTeX_Math の斜体）を `document.fonts.load` で読み、届いてから組む。

### 結果

手元（Apple Silicon）の Core Web Vitals の計測（0050）。

| | 前 | 後 |
|---|---:|---:|
| LCP（最も悪いページ） | 2.24 秒（`heavy-long`） | 1.95 秒（`complex-nesting`） |
| `/articles/heavy-long` の LCP | 2.20 秒 | 1.92 秒 |
| CLS（最も悪いページ） | 0.017（`complex-mixed`） | 0.000 |
| `/articles/heavy-math` の CLS | 0.004 | 0.000 |

CI の機械の遅さを、CPU を遅くする倍率（`WEB_VITALS_CPU_THROTTLE`）で手元に再現して比べた。改善前の版では、7 倍で `/articles/heavy-long` が 2.51 秒、8 倍で 2.83 秒になり、CI の 2.75 秒はこの間に当たる。

| CPU の倍率 | 前：`heavy-long` | 前：最も悪いページ | 後：`heavy-long` | 後：最も悪いページ |
|---|---:|---:|---:|---:|
| 7 倍 | 2.51 秒 | 2.51 秒 | 2.04 秒 | 2.18 秒（`complex-nesting`） |
| 8 倍 | 2.83 秒 | 2.83 秒 | 2.10 秒 | 2.18 秒（`complex-nesting`） |

CI でも上限まで 0.3 秒ほどの余裕がある見込みである（CI で確かめるまでは見込み）。

Lighthouse では、`unsized-images` と、KaTeX のフォントの警告（`font-display-insight`）がなくなり、`/articles/heavy-long` の Total Blocking Time が 210 ms から 100 ms になった。

## 実装しないこと

- 文中の数式の高さの正確な見積もり。組む前の TeX の文字列は組んだ後より長く、二行に折り返すと、行の高さを合わせても下の行がずれる（`/articles/complex-mixed` で 0.0125 が出ることがある）。
- 表の拡張（`micromark-extension-gfm-table`）を、表のない本文で外すこと。長い記事の解析の約 3 割を占めるが、先頭の部分だけを解析するようにしたので最初の描画への効き目は小さく、長いタスクの残る `/articles/heavy-long` は表を含むので効かない。
- 全体の解析を、いくつかのタスクに分けること。`/articles/heavy-long` では、最初の画面の後の全体の解析が 140 ms ほどの長いタスクとして残る（Total Blocking Time 100 ms）。本文を分けて別々に解析すると、脚注の番号と脚注の欄が分かれた部分ごとになり、結果が変わる。
- 最初の要求の連鎖（HTML、本体の JS、後から読み込むチャンク）をなくすこと。Lighthouse の `network-dependency-tree-insight` は、HTML から本体の JS への連鎖だけでも 0 点になる。後から読み込むチャンク（KaTeX、リンクカードの部品）は、描画に要らないので先読みしない。
- 使わない JS（`unused-javascript`、ページごとに 21〜26 KB）を、ページの種類ごとのチャンクに分けること。記事のページで、本文を描くのに要るチャンクの取得が一段遅れ、LCP がかえって遅くなる。

## テスト設計

- 先頭の部分（vitest）：最低の文字数の後の、空行の後の見出しで切ること。短い本文、見出しのない本文は切らないこと。フェンス、数式、`:::`（入れ子を含む）、`<pre>`、コメントの中、字下げした見出し、段落の直後の見出しでは切らないこと。後ろの一行の定義を足し、足せない形の定義（複数行の脚注、段落の続き、引用やリストの中、`:::` の中）があれば切らないこと。コードの中の定義のような行は足さないこと。見本のすべての記事で、先頭の部分を描いた結果が、全体を描いた結果の先頭と一致すること。
- 画像の大きさ（cargo test）：PNG と、拡張子のない PNG、SVG の `width` と `height`（px を含む）、`viewBox`（カンマ区切り、小数）を読むこと。% や em、片方だけ、壊れた開始タグ、画像でないファイル、壊れた画像は大きさなしにすること。`stroke-width` などの別の属性を読まないこと。DB の `media_sizes` に入ること。
- 数式（vitest）：ブロックの数式の高さの見積もり（分数の有無、行を分ける環境、行列）。文中の `\dfrac` だけ行を高くすること。
- E2E：長い記事を最後の見出しと脚注の欄まで描き、脚注の欄が一つだけ本文の最後にあること。本文の画像に、SVG の大きさの `width` と `height` が付くこと。

## トレードオフ

- 長い本文は、最初の画面の後に、解析をもう一度行う（先頭の部分と全体）。CPU の使用は増えるが、最初の画面に出るのは早くなり、長いタスクは分かれる。
- 少しずつ描き足している間（数フレーム）は、本文の後ろの部分がまだない。ページ内の検索や、すぐに最後までスクロールしたときに、少し遅れて出る。
- 数式の高さの見積もりは、実際の高さと最大で 0.6rem ほど違い、その分のずれは残る。
- KaTeX を組むのが、よく使うフォントが届くまで遅れる（遅い 4G で 2 つのフォント、合わせて約 43 KB）。
- 画像の大きさを読む処理が組み立てに加わる（ヘッダだけを読むので軽い）。
