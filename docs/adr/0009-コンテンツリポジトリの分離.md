# 0009 コンテンツリポジトリの分離

## 状態

採用。
0001 と 0004 の「記事の Markdown はこのリポジトリの `content/` に置く」を置き換える。
0003 の CI を、コンテンツリポジトリを取り込む形に改める。

## 決定

このリポジトリはツール（スキーマ、ビルダー、SPA、デプロイの設定）だけを持ち、記事などのコンテンツは別のリポジトリで管理する。

### コンテンツの扱い

- `content/` を削除し、動作確認用のサンプルとして `example/` を置く。`example/` はコンテンツリポジトリと同じ構成を持つ。
- コンテンツリポジトリは、ルートに `site.toml`、その下の `content/` に `posts/`、`articles/`、`pages/` を持つ（`site.toml` と `content/` のほかの中身は ADR 0010）。
- `site/` は `.gitignore` に入れる。コンテンツリポジトリをこの名前でチェックアウトしても、誤ってコミットされない。

### ビルダー

- 引数を `sqlite-cms [SITE_DIR] [--public <DIR>]` に改める。`SITE_DIR` はコンテンツリポジトリのルート（既定は `.`）、`--public` は配信用ディレクトリ（既定は `public`）で、DB はその下の `db/` に書き出す。
- `SITE_DIR` の既定を `.` にするのは、コンテンツリポジトリの中でバイナリを実行する使い方で引数を省けるようにするためである。
- 書き出し先を DB のディレクトリではなく配信用ディレクトリのルートで受けるのは、マニフェストに書く URL（`/db/...`）と書き出し先の対応を崩さないためである。
- マイグレーションはビルドスクリプトで `migrations/*.sql` を列挙し、`include_str!` でバイナリに埋め込む。ファイルを足せば次のビルドで自動的に取り込まれる。
- `content/` が存在しなければエラーとする。`posts/` などの下位ディレクトリの欠落は、従来どおり空として扱う。

マイグレーションを埋め込むのは、スキーマをツールの側に固定するためである。
スキーマは SPA のクエリと対になっており、どちらもこのリポジトリが持つ。
バイナリが実行時にマイグレーションのディレクトリを探す方式では、コンテンツの場所からの相対位置という、ツールとコンテンツの配置に依存する取り決めが要る。

### npm スクリプト

- `build:db` は環境変数 `SITE_DIR` のディレクトリを使い、未指定なら `example/` を使う。開発時はサンプルでそのまま動く。
- `deploy` は `SITE_DIR` が未指定なら止まる。サンプルが本番に出ることを防ぐ。

### CI

- リポジトリ変数 `CONTENT_REPOSITORY`（`owner/repo`）でコンテンツリポジトリを指定し、`site/` にチェックアウトして `SITE_DIR=site` でビルドする。
- 非公開のコンテンツリポジトリには、シークレット `CONTENT_REPOSITORY_TOKEN` で読み取り権限のあるトークンを渡す。未設定なら `GITHUB_TOKEN` を使う（公開リポジトリならこれで足りる）。
- 契機は `main` への push、手動実行、`repository_dispatch`（種別 `content-updated`）の三つ。
- `CONTENT_REPOSITORY` が未設定ならデプロイを止める。`posts/` などの欠落は空として扱うため、止めなければ空のサイトで公開中のサイトを上書きしてしまう。

## 実装しないこと

- コンテンツリポジトリ側のワークフロー（push で `content-updated` を送るもの）。コンテンツリポジトリはまだ存在しないので、この ADR では受け口だけを用意する。
- コンテンツのバージョン固定（特定のコミットを指してビルドする）。常に既定ブランチの最新を使う。

## テスト設計

`cargo test` で次を検証する。

- 埋め込まれたマイグレーションが、ファイル名の昇順ですべて含まれること。
- `content/` が存在しないとビルドが失敗すること。
- 引数の解釈（`SITE_DIR` と配信用ディレクトリの既定、`--public` の上書き、`--help`、余分な引数、`--public` の値の欠落）。

次は手元で確認する。

- リポジトリの外にあるコンテンツで DB を生成できること。
- 別のディレクトリからバイナリ単体で実行できること（マイグレーションの埋め込み）。
- `migrations/` に SQL ファイルを足すと、再ビルドで埋め込まれること。
- `SITE_DIR` なしの `npm run deploy` が止まること。

## トレードオフ

- コンテンツを更新しても、コンテンツリポジトリから通知を送る仕組みを入れるまでは、デプロイを手動で起動する必要がある。
- 公開される内容は、ツールのコミットとコンテンツのコミットの組で決まる。二つのリポジトリの組み合わせを一つのコミットで固定できないため、過去の公開状態を再現するには両方の履歴を突き合わせる必要がある。
- マイグレーションの埋め込みで、スキーマの変更にはバイナリの再ビルドが要る。CI は毎回ソースからビルドするので、運用上の手間は増えない。
